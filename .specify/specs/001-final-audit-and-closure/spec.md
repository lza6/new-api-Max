# Spec 001：终局闭环总审计 / 主动补位 / 真实验收 / 深度反向修复

> 性质：对已生产部署的 new-api-Max 网关进行最严格的全量终局审计 + 补漏 + 修复 + 验证 + 文档同步，
> 直到每个 backlog 节点真实闭环。本 spec 依据项目宪法（.specify/memory/constitution.md）。

## 1. 背景与目标
- 系统已生产运行（freeapi.tingfengai.art，v1.2.35），真实用户/调用方接入中。
- 大量功能分批开发（B2-B5、前端 8.x、运维增强），需要**证据化状态矩阵**与**补位闭环**，而不是"看起来有"。
- 目标：形成真实可运行、可调用、可计费、可审计、可维护、可交付的产品闭环，并沉淀 SOP 与审计账本。

## 3. 审计需求（R）
- R1 功能闭环矩阵：逐项定位代码 + 证据文件 + 状态（DONE/PARTIAL/MISSING/BROKEN），写入 `计划书/audit/closure-matrix.md`
- R2 前后端契约与错误人话：抽查关键端点（logs stat/traffic、auth、token、channel、task events、pricing、user），
  请求/响应字段与前端类型/调用一致；错误码→人话映射全覆盖；契约防坑测试
- R3 SQL/DB：慢查询模式（logs/tasks/usage 聚合 WHERE）、缺索引清单、近期迁移三库兼容抽查、SQL 注入/锁/死锁风险 → `计划书/audit/sql-db.md`
- R4 稳定与安全：限流/全局并发上限/超时/熔断现状；SSRF/web 防护生效；429 退避实测；健康检查/可观测性 → `计划书/audit/resilience-observability.md`
- R5 用户体验补位：S1 会话上限设置、S2 模型测试入口、S3 一键封禁 IP、B2-3 onboarding、hover-why、错误人话、无障碍
- R6 计费安全回归：quota 不变量测试全绿；影子价不改计费；Checkout/预扣/结算链路安全
- R7 文档与 SOP：部署/回滚/排障 SOP、`计划书/audit-ledger.md` 验证账本（防重复跑同一测试）、观察性指标说明
- R8 交付闭环：修复以主题 commit → push → tag → Release → 生产部署（备份+回滚），并留线上验收证据

## 4. 验收标准（总门）
- [ ] 每个 backlog 节点有明确状态 + 代码/证据定位，无"宣称完成但无证据"
- [ ] 关键契约与错误人话抽查通过；计费不变量测试全绿
- [ ] 发现的 P0/P1 缺陷全部修复并验证；P2 有明确排期
- [ ] 前端质量门（tsgo/build/vitest/i18n）全绿（存量失败有基线证据 + 排期）
- [ ] SOP 与 audit-ledger 落地；workflow_status.md 反映真实进度
- [ ] 修复版本 Release + 生产部署 + 线上验收证据

## 5. Open Questions / 假设（Clarify 阶段待用户确认，不阻塞 Phase A）
- Q1 登录会话上限：按"每用户同时在线设备数"实现（默认关）？上限值默认几？（假设：默认关；开启后每用户上限 3 设备）
- Q2 一键封禁 IP：仅 root 可用？默认封禁时长？（假设：root 可用；默认永久+可解封）
- Q3 本批修复优先级：S1-S4（用户已报问题）+ R6 计费安全 > 功能补位（B2-3/B2-4） > 架构项（B3-1/B4-1/B5-2/3/4/5 中未完成部分）？

## 6. 非目标（Non-Goals）
- 不做无关重构/目录搬迁（除非审计发现阻塞性屎山且用户确认）
- 不引入新基础设施（K8s/Kafka 等）——仅输出可执行建议
