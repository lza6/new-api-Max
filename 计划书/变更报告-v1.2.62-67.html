一、上下文与直觉

本阶段围绕三条主线推进：(1) 生产稳定性收口——B4-1 提交误删任务落库属真实生产回归（任务行不落库、internal_task_id=0、轮询/SSE 断链），优先修复；(2) 网站权威性与可观测性——流量统计此前只会显示 MB、无站点累计口径、无带宽排行，且"模型广场/系统信息"存在展示缺口，需要"一次请求能查清、首页数字是真的"；(3) 订阅商业化——存量订阅基建（套餐/余额购买/支付/分组升级）已很完整，缺的是"档位化"能力：并发/RPM 限流→429、模型×套餐访问矩阵、每用户档位覆盖、周卡单位。

直觉判断：能复用存量组件/表结构的一律复用（如套餐 CRUD、`InMemoryRateLimiter`、gopsutil 采样、consume log 持久列），新增只做"缺口最小增量"；限流与矩阵校验一律 fail-open（无订阅/配置损坏/DB 不可用不拦截），避免新功能误伤存量请求。

三、设计要点（直觉落地）

  • 计费/资金不变量：本次未触碰任何计费数值口径；订阅覆盖仅影响限流，不改额度。
  • 限流叠加语义：订阅档位与既有 token/分组/全局并发并存，任一超限即 429（取最严），不绕过既有防线。
  • 三库兼容：新列均为 GORM bigint/text 标准列，聚合用 COALESCE(SUM(...)) 与 COUNT(*)；SQLite 已验证。
  • fail-open 原则：矩阵/档位解析任何异常都放行，保证新功能上线不误伤存量流量。

五、变更测验（请回答，答案在下方折叠）

  1. v1.2.62 修复的生产回归是什么？为什么它会导致任务轮询/SSE 断链？
  2. 站点权威统计的"总带宽"来自哪两个持久化列？为什么不直接扫 other JSON？
  3. 订阅档位限流超限返回什么状态码？"覆盖"和"套餐档位"谁的优先级更高？
  4. 模型矩阵校验在什么条件下 放行（fail-open）？请列出至少三种。
  5. 系统信息页 CPU/内存不显示的根因是什么？v1.2.64 怎么修的？
  6. 模型广场卡片上的"成功数"口径是什么？（成功 = ？）
答案
  1. B4-1 提交误删了 executeTaskSubmissionWith 成功路径的 task.InsertWithContext，任务行从不落库（internal_task_id=0），轮询/续传查不到任务，SSE 断线续传失去锚点。
  2. request_bytes + response_bytes 持久化列；扫 JSON 无法用 SQL SUM，百万级会慢查询。
  3. 429；覆盖（RpmOverride/ConcurrencyOverride）优先，0=回退套餐档位。
  4. 无 active 订阅、套餐 Models 为空（""/[]）、配置损坏（非 JSON）、DB 不可用（model.DB == nil）、模型名为空。
  5. 资源采样被"性能监控开关"门控，开关关闭后 GetSystemStatus() 恒为 0；v1.2.64 把 5s 采样与开关解耦（开关只控制 middleware 超载拒绝）。
  6. 成功 = consume 计费日志数；总数 = consume + error 日志数（错误日志也带 model_name）。
