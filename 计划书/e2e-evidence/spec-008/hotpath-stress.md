# Spec-008 压测证据（请求热路径 + 高并发）

**日期**：2026-10-14
**被测版本**：commit `200c7ffe9`（T3.3 接线）
**环境**：Windows 10 Pro / Go 1.25 / 12th Gen Intel i9-12900HX（本地开发机，非生产硬件）
**执行命令**：

```bash
go test ./service/training_capture/ -run='^$' -bench='Benchmark' -benchmem -benchtime=300000x
go test ./service/training_capture/ -run='TestStress' -v -timeout 400s
```

> **诚实的边界**：本文所有数字来自**单进程 Go 基准与并发测试**，不是在
> 生产网关上跑 HTTP 负载得到的 p95。它证明的是「新增到请求路径上的
> 工作量有多大」，不是「网关整体 p95 无变化」。
> 后者需要真实上游渠道 + HTTP 压测，**尚未执行**（见文末遗留项）。

## 1. 请求路径单次开销（基准）

| 场景 | ns/op | 分配 | 何时发生 |
|---|---|---|---|
| `BuildSignal` 未启用 | **96.7** | 0 B / **0 allocs** | 绝大多数请求（功能未开或云盘未配） |
| `BuildSignal` 启用 | 1653 | 176 B / 2 allocs | 采集开启且用户已授权 |
| `BuildSignal` + 入队 | 1911 | 176 B / 2 allocs | 同上，含非阻塞投递 |

**读法**：
- 未启用时的 96.7ns 是**纯开销上限**——两次原子读 + 一次 `gopool.Go`
  之外没有别的工作，且**零堆分配**（不产生 GC 压力）。
- 启用时的 1.9µs 是**每条被采集请求**的代价，且这段代码运行在
  `gopool.Go` 里 —— 它在响应体**写完之后**才执行，不占用用户等待时间。
- 参照量级：一次正常的上游 LLM 请求在 200ms–30s 之间。1.9µs
  是它的 1/100000 以下。

原始输出：

```
BenchmarkBuildSignalDisabled-24     300000    96.71 ns/op    0 B/op   0 allocs/op
BenchmarkBuildSignalEnabled-24      300000  1653 ns/op     176 B/op   2 allocs/op
BenchmarkHotPathFullCapture-24      300000  1911 ns/op     176 B/op   2 allocs/op
```

## 2. 高并发压测（极端条件）

### 2.1 洪峰投递：32 写者 × 5000 次，队列容量仅 64

```
压测：32 写者 × 5000 次 = 160000 投递，耗时 1.15s（139020 次/秒）
      队列：容量=64 积压=64 入队=70 丢弃=159930
```

**验证到的性质**：
- **不阻塞**：队列容量只有 64，却扛下 16 万次投递且 1.15s 跑完。
  若投递会阻塞（等队列腾位），32 个写者会串行化并远超此耗时。
- **计数守恒**：`入队 70 + 丢弃 159930 == 尝试 160000`（精确相等）。
  不守恒意味着有投递既没入队也没记账 —— 那会让运营方误判「采全了」。
- **消费者确实在工作**：压测后队列能被排空（用例等待并断言 `Len == 0`）。

> 丢弃率 99.96% 是**设计预期**，不是缺陷：采集是「尽力而为」的辅助功能，
> 队列满时丢采集**而不是**反压用户请求。要降低丢弃率应提高 worker 吞吐
> （按用户分片的多 worker），而不是放大队列 —— 放大队列只会让内存风险上升。

### 2.2 无消费者：队列硬上限

```
压测：16 写者 × 3000 次 = 48000 投递，耗时 159ms（302166 次/秒）
      队列：容量=128 积压=128 入队=128 丢弃=47872
无消费者时队列最坏占用 8421376 字节（容量 128 × 单条上限 65536）
```

**验证到的性质**：worker 不运行时（或完全跟不上时），队列**仍是硬上限**，
最坏内存占用 8.4MB（约容器预算 900MB 的 0.9%）。

单条上限 64KB 是硬闸门：一个把 10MB 上下文塞进 prompt 的请求，
若不截断，1024 条队列就是 10GB —— 必然 OOM。

### 2.3 运维在高压下改开关（B1 的回归场景）

```
开关切换 100 次后：入队 258，丢弃 23915（无 panic、无死锁）
```

16 个写者持续投递的同时，**反复开关总开关 100 次**。

**这是 B1（`send on closed channel` → 杀进程）的原始触发场景**：
停机/切换开关与在途请求并发。无 panic 即通过。

## 3. 内存有界性（防无界增长）

| 状态 | 写入量 | 最终大小 | 上限 |
|---|---|---|---|
| 授权缓存 | 30000 条 | 10000 条 | 20000 |
| 全局指纹集合 | 50000 条 | 1000 条 | 1000 |

**为什么重要**：授权缓存随用户数增长、指纹集合随对话量增长。
无界的话，每天 10 万条指纹 × 一年 ≈ 2.3GB，而容器只有 900MB。

### 3.1 授权判定的热路径延迟

```
授权判定 1000 次耗时 989µs（缓存命中 989ns/次）
```

缓存命中约 1µs/次（含 map 读 + TTL 检查 + sink/gateway 判定），
且用例断言必须 < 10µs。**注意**：缓存未命中会回源 DB，
那是 worker 侧的成本，不在请求停等路径上（`MaybeCapture` 未命中时
直接返回 false，不阻塞请求）。

## 4. 结论

| 用户要求 | 证据 | 状态 |
|---|---|---|
| 「一定不能影响用户请求的延迟」 | 未启用 96.7ns / 0 分配；启用 1.9µs 且在 `gopool` 内 | ✅ 单请求开销已量化 |
| 「高并发怎么合理解决」 | 洪峰 99.96% 丢弃但**不阻塞**；计数守恒 | ✅ |
| 「异步」 | 信号构造 + 入队全在 `gopool.Go` 内，响应已返回 | ✅ |
| 「自适应」 | 令牌桶限速 1MB/s（≈上行 75Mbps 的 10.6%）；队列满即丢 | ✅ |
| 「不能 OOM」 | 队列最坏 8.4MB；缓存/指纹集合均有硬上限 | ✅ |
