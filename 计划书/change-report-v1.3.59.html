commit 6a08f6f55 · tag v1.3.59 · 2026-09-29 · 已零停机上线生产（切流耗时 4 秒）

1. 上下文（Context）

生产用户反馈三类痛点：
① 「复制密钥要验证」——已登录用户查看自己的 API Key 仍被要求二次验证；
② 渠道 Key 运维缺失——管理员无法直接新增 key、无法单独测试某个 key、无法批量一键测试；
③ 迭代期请求中断——docker compose up 先停后起，造成 5-15s 全站不可用。

2. 直觉（Why）——设计取舍

  • 真正的安全边界是「归属」，不是「再问一次」。后端 GetTokenByIds(id, userId) 已保证只能读自己的密钥；用户已通过 session 登录，再要求一次 step-up 只是重复校验，纯增操作成本。
  • 兼容优先，不靠配置端点。前端改为「先免 proof 请求 → 仅当服务端返回 SECURITY_PROOF_* 时才弹验证并重试一次」。这样无论站点开关怎么配，前端都对，不需要额外的能力探测接口。
  • 开关可回滚。两个新开关（自己密钥 / 渠道密钥）默认关闭验证，改回 true 即恢复旧行为——安全策略归管理员，不写死。
  • 蓝绿交替端口而非双实例常驻。2C2G 内存吃紧，双后端常驻不现实。改为：发布时短暂共存（实测 new-api 仅 141MiB，可用 1065MB），健康后切 Caddy 上游（caddy reload 毫秒级），再停旧容器——平时仍只有一个实例。
  • 新容器以 NODE_TYPE=slave 启动。后台任务（订阅重置/清理/授权同步）都由 IsMasterNode 门控，slave 不会与旧容器重复执行。
