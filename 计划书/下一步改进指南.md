## 0. 如何使用本指南（先读这里）

1. **按优先级取批**：P0（性能/稳定性/安全）→ P1（体验/可观测性/插件）→ P2（新方向）。同一主题内按「依赖→实现→验证」顺序执行任务卡。
2. **一次只做一批**：禁止「前面改 bug、后面加功能又出新 bug」的穿插；每批独立提交（主题 commit），改完先本地全量验证，再走部署+线上验收。
3. **TDD 是硬要求**：每个原子任务先写失败测试（红）→ 最小实现（绿）→ 重构；验证命令必须真实运行并把输出存入 `计划书/e2e-evidence/`。
4. **禁止假实现**：未跑通不算完成；无法在本机验证的（真实上游、真实浏览器、生产库）明确标「待验证」并给出服务器验证步骤。
5. **保护现有工作**：不 `git reset/clean`、不全量覆盖、不 `-f` 推送；涉及数据库 schema 的改动必须跑 SQLite/MySQL/PostgreSQL 三库矩阵。
6. **文档维护**：本文件夹（`计划书/`）是规划文档的唯一存放处；执行后回填「完成记录」到对应任务卡，并刷新 `graft build`（代码图）。

### T1 热路径性能冲刺（P0 · 目标：单并发附加 19ms → 10ms）

**背景与根因（证据）**
- `workflow_status.md` 成对基准：异步 consume-log flusher 落地后，顺序 overhead p50 27.6→18.8ms；并发 50 p95 645→140.6ms。
- 剩余 19ms 来源：`model/consume_log_flusher.go` 入队路径里 `RecordConsumeLog` 内仍同步做 `GetUserSetting`（用户设置 DB 读）与结算 quota 更新；`MEMORY_CACHE_ENABLED` 已默认 true，但**用户设置仍未缓存**。
- 目标 10ms 的对标依据：直连上游 p50 约 60-90ms，网关额外 10ms 内才算「透明代理」。（`计划书/e2e-evidence/paired-latency-bench-v1.2.34.json`）

**方案对比**

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A. 用户设置只读缓存 | 启动/更新时加载用户级设置到内存 map + Redis，`GetUserSetting` 走缓存，失效订阅 TTL | 见效快、改动小、可回滚 | 缓存一致性要管 | **推荐（先做）** |
| B. 结算批量异步 | 预扣/结算改队列异步落库（类似 consume-log flusher） | 彻底移除同步 DB 写 | 计费链路风险高（失败补偿、审计） | 属 L3 计费改造，需单独审批后做 |
| C. Redis 令牌缓存 | 生产已有 Redis，令牌校验结果缓存 | 减少 token 查询 | 撤销延迟窗口 | 与 A 同批做（可配置开关） |

**原子任务（TDD）**

1. **用户设置缓存抽象**
   - 文件：`model/user_setting.go`（或现有 setting 层），新增 `GetUserSettingCached(userID, key)`。
   - 变更：内存 map + TTL（默认 30s，`USER_SETTING_CACHE_TTL` env）+ Redis 二级（可选）；失效点：写设置、用户删除。
   - 验收：缓存命中/未命中/失效后重载三态单测；`go test ./model/ -run UserSetting` 绿。
   - 风险：多实例一致性问题——用 Redis 作强一致回源，内存仅当 `MEMORY_CACHE_ENABLED=true`。
2. **热路径接入**
   - 文件：`model/consume_log_flusher.go` / `service/log_info_generate.go`（RecordConsumeLog 链）。
   - 变更：结算前置读取改用缓存；行为等价，默认开关关→零行为变化。
   - 验收：异步/同步两条路径单测均绿；回归 `go test ./model/ ./service/`。
3. **基准脚本入库**
   - 文件：`scripts/bench-latency.ps1`（成对 N=60 + 并发 20/50，复用已有基准方法）。
   - 变更：一键跑直连 vs 网关对照，输出 JSON 到 `计划书/e2e-evidence/`。
   - 验收：本机跑出 overhead p50 前后对比，目标 ≤10ms（若未达，如实记录并给出下一步根因）。
4. **429/4xx 透传复核**
   - 文件：`controller/relay.go`、`service/relay_error_class.go`。
   - 变更：无重试预算时上游 4xx 原样透传（不透传包装成 500）；补 4xx 透传单测。
   - 验收：`go test ./service/ ./controller/` 绿；本地 mock 上游 400/429 验证透传。

**验证命令**

```powershell
go vet ./... ; go build ./...
go test ./model/ ./service/ ./controller/ ./relay/... ./common/...
cd web ; bun run typecheck ; bunx vitest run ; cd ..
powershell -File scripts/bench-latency.ps1   # 前后对比，目标 p50 <= 10ms 附加
```

**回滚**：缓存/透传均为行为开关化（默认关），改回 env 即回退；结算异步若做需 L3 审批 + 备份 `docker-compose.yml` 后重启。

**完成定义**：附加延迟达成或诚实报告差距；四条任务验收全勾；证据 JSON 入库；主题 commit。

| C. stream_fallover 默认开 | 流式首字失败自动换渠道 | 增强容错 | 需灰度验证 | 与 A 分两小步 |

**原子任务（TDD）**

   - 验收：单测证明坏分渠道不被选中（受控权重表）；默认关无回归。
3. **stream_fallover 灰度→默认**
   - 文件：stream 通道 failover 逻辑 + 开关默认值。
   - 变更：先灰度环境验证 24h（记录切换次数/成功率），再翻默认。
   - 验收：线上观测无「fallover 引发重复计费」证据（消费日志对账）。
4. **前端概览接入**
