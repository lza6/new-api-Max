## 7. 方案对比（至少三种，含权衡矩阵）

### 方案 A —「发布闭环与门禁可信优先」（Reliability-first）

**内容**（约 120 字）：先把「能不能发布、能不能验证」这条链修通。恢复部署通道（SSH 密钥/CI 部署、或明确指定的代部署人）；建立**单一版本真相源**（`VERSION` 唯一 + `workflow_status.md` §0 声明线上版本 + tag 与部署绑定）；把本地全量测试拆成可完成的**分片矩阵**（逐目录、记录耗时与退出码），把 controller 的 7–9 个顺序依赖用例改成各自自持 DB；清理工作区 71 项并救回被删的 766 行前端计划。产出 v1.3.167。

**优点**：解除对所有后续工作的证据封锁；后续任何修复都能被门禁保护。**缺点**：不直接产生用户可见价值，纯工程投入（预估 2–3 天）。**风险**：低（多为测试/文档/脚本层改动，唯一高风险是 controller 测试改造可能掩盖真实顺序缺陷）。

### 方案 B —「Web 性能与体验优先」（Web Vitals-first）

**内容**（约 130 字）：直攻 LCP 3704ms。语言包（172KB gzip，7 语言 × 530–772KB raw）是唯一剩余瓶颈。三选一：① 按路由拆分 i18n 命名空间（首屏只加载公共壳 + 当前路由命名空间）；② 裁剪 key（当前 6842 key，其中多少在首屏路由可达？需实测）；③ 接受慢网英文闪切（保留 en 作 fallback 并立即 render）。同时收口 4 条 UX P1（抽屉未保存保护、16 个设置分区的导航守卫、a11y 两处）与 4 条 flaky 用例。产出 v1.3.169–171。

**优点**：用户直接可感（移动端首屏、数据丢失防护）；有现成测量脚本（`fe-vitals.cjs`）可前后对照。**缺点**：语言包拆分触碰 1453 个 tsx 的 `t()` 调用路径 + 7 份 locale 资产，是**面广的机械改动**，回归面大；且需产品拍板。**风险**：中（拆错命名空间 = 部分文案显示 key，属用户可见故障）。

### 方案 C —「财务与计费真相优先」（Billing-truth-first）

**内容**（约 130 字）：把「钱算得对不对」变成可证命题。① Claude 计费两处：先写**决策请求单**（两种语义的业务后果、影响面、影子对照方案、回滚路径），业主拍板后用 shadow 模式在非生产分组对照，再改；② Stripe `StripeUnitPrice` 语义先定；③ 起真实 ClickHouse 验证日志分库与 `cost_quota`/`cost_rule_id` 列；④ 成本覆盖率口径固化（`cost_tracking_since` + 「历史不可追溯」文案）。产出 v1.3.168。

**优点**：直接消除最贵的风险（真实扣费错误 + 财务虚高 + 日志写不进去）；本项目已有惨痛先例（225 次多扣费 / 补偿 $20.86），投入产出比最高。**缺点**：两条决策**必须业主拍板**，无授权即阻塞；CH 验证需起容器（本机 Docker 情况未验证）。**风险**：中高（动计费 = 红线区，必须有影子对照与回滚）。

### 推荐：**A → C → B**（串行，不并行）

**理由（证据驱动）**：

1. **A 是 C 和 B 的前置**。C 的计费改动必须有影子对照与门禁保护，B 的性能改动必须有可靠回归——而当前「本地全量测试跑不完」+「无部署通道」+「线上版本不可探测」意味着**任何修改都无法被证明没坏**。先付这笔「证据税」，后面所有工作的结论才能立得住。
2. **C 的经济价值最高但可以晚一步**：Claude 计费缺陷的影响面取决于实际有多少请求命中 cache 计费，需先量化（这件事本身属于 A 的可观测性产出）。
3. **B 放最后但必须做**：语言包问题已经过两轮优化仍未解决，且它需要产品决策；放在 A/C 之后做，能用 A 建立的门禁保证「拆命名空间」这类面广改动不破坏文案。

## 11. 质量门禁与证据要求

1. **四级标签强制**：`已验证` / `静态确认` / `合理推断` / `待验证`。任何「已完成」必须写明是哪一级。
2. **未实际运行 ≠ 通过**：`go test` / `bun run build` / E2E 的「通过」必须附命令与真实输出摘要（含耗时与退出码）。
3. **mock 不得冒充集成**：SQLite + mock 上游的压测结果只能证明「代码路径可执行」，不得描述为容量结论。
4. **审查门禁**（`policy.md` §4）：代码改动必须过独立只读 reviewer，最多 3 轮；超轮次记录剩余问题并标阻塞，**不得伪造 Approve**。
5. **覆盖率**（`policy.md` §1）：单元+集成+E2E 合计 ≥80%，纯逻辑模块 100% 分支；不达标必须在 `test_ledger.md` 写「未覆盖分支 + 原因」。
