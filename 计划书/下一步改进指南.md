5. **三库铁律**：任何触碰数据库的改动，必须在 SQLite + MySQL + PostgreSQL 三库上验证（项目 AGENTS.md 强制）。验证方式见 §6。
6. **i18n 铁律**：前端所有新增文案走 `useTranslation()` + 英文键，`zh.json` 提供 fallback。不许硬编码中文进组件。
7. **JSON 铁律**：root 模块所有 JSON 操作必须走 `common.Marshal/Unmarshal`（AGENTS.md:80-91），**本指南同时要求把"新增代码 0 违反"作为验收项**；存量违反在 Batch-7 统一清理，不在此扩大。
8. **测试规范**：新测试用 `testify/require`+`assert`；不写凑覆盖率的无效测试（AGENTS.md 后端测试质量节）。
9. **relaykit 独立**：任何 `relaykit/` 改动后必须跑 `cd relaykit && GOWORK=off go build ./...`。
10. **风格一致**：新代码匹配周边代码风格（早期 return、命名、注释密度）。

## 1. 战略总览：v1.0.0-max.2 → v1.1.0

### 1.1 版本主题：「透明网关」（Transparent Gateway）

对标参考集（1015 项目）反复收敛出的三个用户痛点：
- **信任痛点**：渠道"挂羊头卖狗肉"（转卖便宜模型/虚报缓存命中）无法被发现 → 渠道验真
- **可靠性痛点**：流式请求一旦开始无法切换渠道；任务提交超时被盲退款 → 流式 fallover + 三态提交
- **透明度痛点**：用户看不懂"为什么扣这么多钱/为什么选这个渠道" → 日志解释卡 + 退款可见性

### B1-1 密钥日志指纹化

**问题根因**（N1/N16 证据）：错误路径与调试日志可能携带完整上游 key；日志是泄露的头号通道。

**步骤**：

1. 新建 `common/secret_mask.go`：
   ```go
   // MaskKey 返回形如 sk-****abcd 的指纹。full 显示为前 4 后 4，中间以 **** 替换；
   // 长度不足 12 的 key 只保留末 4 位。用于日志与错误消息，不用于任何匹配逻辑。
   func MaskKey(key string) string
   // MaskMessage 扫描消息中疑似 key 的片段（长度>=20 且匹配配置的 key 前缀集合）并替换为指纹。
   func MaskMessage(msg string) string
   ```
   - key 前缀集合从现有渠道定义提取（`sk-`、`sk-ant-`、`AIza` 等，在 `relay/channel/` 各 adaptor 的构造处核对真实前缀，以代码为准不臆造）
   - `MaskMessage` 实现用一次 `strings.Builder` 线性扫描，禁止正则回溯
2. 接入点（只加不改）：
   - `service/channel.go` / `controller/channel.go` 中所有把 `channel.Key` 拼进 error/log 的位置 → 包一层 `MaskMessage`
   - `logger/logger.go` 的 `SysError`/`LogWarn` 入口统一调用 `MaskMessage`（单点接入，避免逐点改）
   - 渠道测试接口（`controller/channel-test.go`）返回给前端的错误文案 → `MaskMessage`
3. 单测 `common/secret_mask_test.go`：表驱动覆盖（normal/short/empty/多 key 混排/无 key 文本）。

**定位提示（执行 AI 必读）**：`grep "channel.Key"` 在 controller/service 中直接拼日志的实测为 0 处——真实泄露面是：① relay 错误路径透传上游错误体（含上游可能回显的 key/ Authorization 头）② 调试日志 `logger.LogDebug` 全量 dump 请求头。接入以 `logger/logger.go` 出口统一脱敏为主（单点），辅以 `relay/helper` 错误包装处。

## 3. Batch-2：任务资损防线（L1-L2）

> 目标：消灭"已付费但用户被退款"与"退款用户不可见"两类资损/纠纷。核心资产：公共错误分类器。
> 可复用锚点：`service/task_polling.go` 的 8 类 poll failure 分类（`pollClass*`）、`service/task_billing.go` 的 `RecalculateTaskQuota`、`model/task.go` 的 `Task.Data` json 字段。

### B2-1 公共错误分类器（后续 Batch 的地基）

**步骤**：
1. 新建 `service/relay_error_class.go`：
   ```go
   type RelayErrorClass int
   const (
       ErrClassAuth          RelayErrorClass = iota // 401/403：key 失效，不可重试，必须冷却
       ErrClassRateLimited                          // 429：可冷却后重试，尊重 Retry-After
       ErrClassServerError                          // 5xx：可重试（限次），也冷却
       ErrClassTimeout                              // 网络超时：不可确认，走 unconfirmed 流程
       ErrClassBadRequest                           // 4xx 参数问题：不可重试不冷却（我方错误）
       ErrClassCapability                           // 模型不支持该参数：不可重试（参考 aisix UnsupportedCapability）
       ErrClassUnknown
   )
   // ClassifyHTTPStatus 依据 aisix "cooldown 与 retryability 解耦"模型返回 (可重试?, 需冷却?, class)
   func ClassifyHTTPStatus(status int, retryAfter string) (retryable bool, needCooldown bool, class RelayErrorClass)
   ```
   - 429 且 Retry-After 合法 → 冷却时长取 min(Retry-After, 上限 15min)
   - 401/403 → 不可重试但**必须冷却**（否则后续请求都会撞——aisix 教训）
   - 归属 `service/` 而非 `common/`，因为它属于渠道治理域
2. 单测表驱动覆盖全部状态码类 + Retry-After 解析（非法值/超长值/0）
3. **此文件是 B3-1/B3-2/B4-2 的公共依赖，接口一旦冻结不再改签名**

**验收**：
- [ ] `go test ./service/ -run TestClassifyHTTPStatus -v` 全绿
- [ ] 注释中写明四类语义（auth/rate/server/timeout）与冷却/重试正交的模型出处（aisix cooldown.rs 设计思想）

### B2-2 任务 unconfirmed 三态提交

**问题根因**（N10 MoneyPrinterTurbo `volcengine_seedance.py:251` 证据）：提交接口超时/5xx/响应不可读时，远端可能已创建付费任务；现在直接退款 → 资损。

**步骤**：
1. `model/task.go` 新增状态常量（沿用现有 TaskStatus 字符串机制，不新增枚举通道）：
   ```go
   const TaskStatusUnconfirmed = "unconfirmed" // 提交已发出但结果不可确认；远端可能已创建付费任务
   ```
2. `service/task_polling.go`（或 task submit 的公共路径）：
   - 提交超时/网络错/响应不可读时：**不退款**；把已知信息写入 `Task.Data`（json）：
     ```json
     {"submit_state":"unconfirmed","remote_task_id_hint":"<响应中若能提取到的 id，可为空>","failed_at":"<unix>"}
     ```
   - 提取 remote id：各 adaptor 提交响应若非 2xx 但 body 里带 id（如 kling 的 `data.task_id`），尽力提取——在 adaptor 接口加可选方法 `ExtractRemoteTaskHint(body []byte) string`（默认空实现，不破坏现有 adaptor）
3. 轮询兜底：
   - `unconfirmed` 任务进入轮询队列：若 `remote_task_id_hint` 非空 → 直接查远端状态（成功→正常结算；失败→退款并标注）
   - 若 hint 为空 → 按平台语义在有限窗口（默认 30min，配置项 `task.unconfirmed_window`）内查询，超窗 → 退款并在 `Task.Data` 标记 `"resolution":"refunded_after_window"`
4. 计费联动：`RecalculateTaskQuota` 路径不变；unconfirmed 期间不触发预扣结算
5. 单测：模拟提交超时→进入 unconfirmed→hint 兜底查到成功→正常结算全链路；hint 为空超窗退款路径。

**验收**：
- [ ] `go test ./service/ -run TestTaskUnconfirmed -v` 全绿
- [ ] 三库验证：AutoMigrate 无新增列（只写 Data json），双启动幂等
- [ ] 手工：用 mock adaptor（临时测试插件）触发提交超时，观察任务状态与日志（截图）

### B3-1 cooldown/retryable 解耦 + 决策单点化

   ```go
   // DecideCooldown 是唯一冷却决策点：所有 relay 格式的错误路径必须经过。
   // 输入：渠道 id、B2-1 的分类结果。输出：是否冷却、时长。
   func DecideCooldown(channelId int, class RelayErrorClass, retryAfter time.Duration) (cool bool, until time.Time)
   ```
3. 把现有散落调用点逐个改为调用此函数（逐条记录改动清单）；**保持旧行为开关** `channel.cooldown_v2`（默认 off=旧行为；on=新模型）
4. 恢复机制：冷却到期自动恢复（现有机制若已有则复用），配合 B3-3 健康分展示

**验收**：
- [ ] 开关 off 时全量回归：现有渠道测试全部通过（行为零变化）
- [ ] 开关 on 时单测：401→冷却不重试；429+Retry-After→尊重；5xx→限次重试+冷却
- [ ] 所有 relay 错误路径都过 `DecideCooldown`（`grep` 反向验证清单）

### B3-2 流式首包缓冲 fallover

**根因**（N2 free-router `server.mjs:764` 证据）：new-api 流式请求一旦开始无法切换渠道；空响应/瞬时失败只能让用户看到错误。

**步骤**：
1. `relay/helper/`（或流式转发公共路径）新增首包缓冲：
   - 缓冲 SSE 直到出现首个有效 `content`/`tool_call`/`reasoning` 增量才向客户端提交响应头
   - 超时上限默认 15s（配置 `relay.stream_first_token_timeout`）：超时未出首包 → 判定该渠道本次失败 → 走现有渠道重试链换下一候选
   - 缓冲内存上限 1MB：超过直接放行（防恶意/异常响应占内存）
2. **开关** `relay.stream_fallover`（默认 off）。off 时行为与现状完全一致（不缓冲，立即透传）
3. 与 B3-1 联动：fallover 触发时走 `ClassifyHTTPStatus` 分类并冷却
4. 单测：mock 三个渠道（第一个发空流/第二个发慢首包 3s/第三个正常）→ 开关 on 时客户端收到第三个渠道的正常流；off 时行为不变
5. **性能注意**：缓冲期间不复制 body（用 `bytes.Buffer` 单次写入），确认无双份内存拷贝（代码审查项）

**验收**：
- [ ] 开关 off 回归零变化
- [ ] 开关 on 集成测试三渠道 fallover 场景通过
- [ ] 压测：单请求缓冲内存峰值 <1MB；并发 100 无泄漏（`go test -bench` 或手工压测记录）

### B3-3 渠道健康分聚合

**步骤**：
1. 新建 `service/channel_health_score.go`：滑动窗口（内存 ring，参考 freellmapi in-flight 模式但简化为进程内）聚合每渠道近 1h：成功率、P50/P95 延迟、B3-1 冷却次数
2. 健康分 0-100：`成功率 70% + 延迟线性分 30%`（对齐 NewAPI-Gateway `model_route.go` 的已验证公式，映射 1.5s~10s）
3. 输出给两处：管理端 API（前端徽章数据源）+ Batch-4 探测结果合并
4. 单测 + 内存上限（每渠道 ring 固定 256 条，防多渠道内存膨胀）

**验收**：
- [ ] 健康分 API 返回真实数据（打真实流量后 curl 验证）

### 15.3 真实 Bug 修复记录（c211e4b29）

**现象**：同一 IP 首个请求之后，5 秒内所有请求（如浏览器加载的每个静态资源）都被 429 `ip_banned` 拒绝 → 页面白屏；压测统计异常（本应 4 次 200 却只有 1 次）；自动封禁从未真正落库。

**根因（第一性分析）**：`service/web_protection_tracker.go` 的封禁缓存 `isIPBannedCached` 把「查询过、未被封禁」的条目（`expiresAt=0`）在命中缓存时当作「永久封禁」（DB 契约中 `expiresAt=0` 表示永久封禁），语义撞车。

**修复**：缓存条目增加显式 `banned bool` 字段；未封禁命中直接返回 false；封禁命中才校验 `expiresAt`（0=永久）。

**验证**：严格档位压测 30 连发 → 4×200 + 26×429 → `banned_ips` 落库（auto/expires_at）→ 重启服务后该 IP 仍 429 ip_banned；浏览器 UI 全流程通过；`go test ./service/ ./middleware/` 全绿。
