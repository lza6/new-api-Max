### 1.6 开放瓶颈（本指南 §4 依据）

> **【P0 · 探针实测复现】** 前两条为**实测复现的真实缺陷**（非静态推断），优先级最高，详见 §4.2：
> 1. **全局并发桶槽位泄漏**（`middleware/global-concurrency-limit.go:120-136`）：release 无条件转移槽位而队首可能已超时离场 → 槽位净泄漏。探针 **1864/2000** 复现；累积后桶自我堵死 → 全站 429。开关默认关，管理员一开即埋雷。
> 2. **配置热更新与热路径读取数据竞争**（`setting/config/config.go:255-269`）：无锁就地替换 map，`-race` 复现；可触发 **不可 recover 的 `fatal error: concurrent map read and map write`**，直接杀死整个网关进程。

其余开放瓶颈：

3. **产品形态单一**：本质仍是「API 网关 + 控制台」，缺面向小白的「零代码干活」产品层；用户仍需自接 Key、读文档、写代码。
4. **新手转化漏斗 4 处断点**（§4.3.7，探针实测）：建 Key 后不闭环、两套引导并存、Playground 默认模型硬编码 `gpt-4o`、模型广场无「去对话」入口。
5. **无记忆/技能沉淀**：无用户级长期记忆；插件是 RootAuth 资产（`router/api-router.go:264`），用户无法沉淀技能。
6. **无 Agent 编排层**：任务是「单次转发+轮询」；`ai-elements` 编排组件 16 个零引用（已备未用）。
7. **可解释性弱**：有 request-id 与审计，但缺「人话化黑匣子」。
8. **路由智能有限**：有健康分/权重/亲和，但无「任务复杂度感知 + 成本感知 + 领域标签」路由。
9. **多模态仅转发**：平台自身不产出成品；任务产物埋在 `usage-logs` 表格单元格里（`task-logs-columns.tsx:281`），`GET /api/task/self` 前端零消费者。
10. **无 MCP 通道**：零 MCP。
11. **安全模型「有原语无接线」**（§4.11.1）：`pkg/jsplugin` 权限/审批/签名/沙箱全实现，但 `ParsePermissions` 生产零调用、审批默认 false、沙箱策略仅打日志。
12. **技术债**：根目录 25MB 临时 db、`logs/` 5.6MB、`coming-soon.tsx` + `auto-skeleton.tsx` 死代码、`idx_logs_traffic` 无效索引、多处硬编码站点模型名、`计划书/ops/ai-compliance-checklist.md` 文档断裂。
13. **前端交互细节**（探针实测）：axe 对比度检查「假绿」、`SkipToMain` 断链、DataTable 无错误态（14 页受影响）、首屏预算无回归保护、12 个业务文件未复用 `confirm-dialog`、`bun run lint` 9 个 error。

## 2. 约束与硬规则（AGENTS 摘要，全文见 AGENTS.md）

- **计费安全不变量**：乘数先 400 上界；配额转换只走 `common.Quota*`；倍率只走 `AddOtherRatio`；饱和走 `*Checked`+`attachQuotaSaturation`；pre-consume 饱和必须额度不足失败。

- **三库**（SQLite/MySQL≥5.7.8/PG≥9.6）真实实例验证；迁移幂等；行锁走 `model.lockForUpdate`。
- **认证/安全**：涉认证改动先读 OWASP（Authentication/Session/Password/Forgot/MFA/OAuth/CSRF Cheat Sheets + ASVS，引用版本+requirement id）；审计事件去敏；服务端强制。

- **文档**：不新建 `docs/` 下文件除非用户要求；证据纪律（未跑命令不声称通过）。

### 4.2 v2.x 性能与稳定性硬化（P0/P1）

> 本节 §4.2.1 / §4.2.2 为**探针实测复现的真实缺陷**（并发探针 1864/2000 复现、`-race` detector 复现），非静态推断。修复优先级最高。

#### 4.2.1 【P0 · 实测复现】全局并发桶槽位泄漏 → 桶自我堵死（全站 429）

- **缺陷**：`middleware/global-concurrency-limit.go` 的 `release()`（:120-136）无条件把并发槽位「转移」给队首等待者（`g.active++` + `close(ch)`）；但队首可能**已经超时离场**——`acquire()` 的 `timer.C` 分支（:104-116）已把 `g.waiting--` 并返回 `(false,false)`，**再也不会 receive 那个 ch**。
- **根因**：槽位交接**无归属仲裁**。`release` 的 `g.active--`（:122-124）与 `g.active++`（:129）相互抵消 → 净泄漏 1 个槽位，且**永久无人 release**。长跑不断累积 → `active >= limit` 恒成立 → 所有新请求排队 → 超时 429。
- **实测证据（探针真实运行）**：
  - 2000 轮「release × 队首超时」交叉探针 → **leaked=1864/2000**（FAIL）。
  - 累积饥饿演示：`limit=2`、200 轮 → **accepted=1 / rejected=199 / finalActive=2**（桶填满后永久无槽可用）。
  - 现有测试 `middleware/global_concurrency_test.go:11-128` 只覆盖 acquire/超时/关闭**三条独立路径**，恰好**无交叉**，故从未发现。
- **生产放大条件**：`GlobalConcurrencyEnabled` 默认 false（`setting/relay_setting/relay_setting.go:93-99`），但管理员一旦开启（前端已有入口），叠加长流式请求占槽久 + 30s 默认超时，**必然触发**。
- **任务**：重写交接语义——让队列元素显式表达交接结果（如 `chan bool`：true=槽位已交接）；`release` 出队后**不预增 active**，由被唤醒方在锁内确认收到槽位才 `active++`；超时方在锁内发现已被交槽时负责 `active--`。等价方案：`release` 出槽写入 `slotToken`，被唤醒方锁内仲裁。
- **涉及文件**：`middleware/global-concurrency-limit.go`（唯一生产文件）。
- **验收**：新增 `TestGlobalConcurrencyReleaseRacesTimeout`（断言 2000 轮后 `active==0`）；现有 `middleware/global_concurrency_test.go` 全绿；`-race -count=5` 0 竞态。
- **验证**：`go test -race ./middleware/ -run TestGlobalConcurrency -count=5`
- **回滚**：单文件 revert；开关默认关，回滚零影响。
- **风险**：中（并发原语重写，需保证 FIFO 与不双放行）。**必须**加「release × 超时」交叉用例。

#### 4.2.2 【P0 · 实测复现】配置热更新与热路径读取数据竞争（可 fatal 杀进程）

- **缺陷**：`setting/config/config.go:255-269` 的 `updateConfigFromMap`——map 走 `json.Unmarshal` 到新建 map 后 `field.Set`（:263，无锁就地替换），struct/slice 走 `Unmarshal(field.Addr())`（:266-268，无锁就地写）。`ConfigManager.mutex`（:28-38）**仅保护 `configs` 注册表，不保护热更新写入**。
- **读侧暴露**：热路径 `relay_setting.go:163-190 GetUserRateLimitTier` 每请求遍历 `UserRateLimitOverrides`/`GroupRateLimitOverrides` map（从中继调用：`middleware/user-rate-limit.go:74`）。
- **写侧可达**：`controller/relay_rate_limit.go:59-62`（`PUT /api/option/relay/rate_limit/overrides/group`，RootAuth，`router/api-router.go:215-222`）；定时 `loadOptionsFromDatabase`（`model/option.go:199-207`，每 `SYNC_FREQUENCY` 秒）。
- **实测证据（`-race` 真实运行）**：并发「热路径读档位」×「管理端保存 relay 配置」→ race detector 同时报两处：① `reflect.Value.Set`（config.go:263 write）vs `GetUserRateLimitTier`（relay_setting.go:168 read）；② `runtime.mapaccess2_fast64`（read）vs `runtime.mapassign`（json Unmarshal write）。
- **后果**：Go 内存模型下 map 并发读写可触发 **`fatal error: concurrent map read and map write`**——该 fatal **不可 recover**，会**直接杀死整个网关进程**（非单请求 500）。触发窗口窄（仅配置保存/周期重载瞬间命中读），但属长跑稳定性致命隐患。**同类结构性风险适用全部 `setting/*` 注册配置模块（20+ 个）**。
- **任务**：方案 A（推荐）——写侧**快照替换 + 读侧快照指针**：为 `RelaySetting` 增不可变快照（`atomic.Pointer[RelaySetting]`），写侧构造新结构体后 `Store`，getter 改 `Load()` 后只读。彻底消除 map 并发读写。方案 B——给配置模块加读写锁（改动面大，20+ 模块数十 getter，易漏）。
- **涉及文件**：`setting/relay_setting/relay_setting.go`、`setting/config/config.go`；热点 getter：`GetUserRateLimitTier`、`GetGlobalConcurrencyGate`、`GetStreamFirstTokenTimeout`。
- **验收**：复现探针（读档位 × 保存配置）0 race；`go test -race ./setting/... ./middleware/... -count=1`。
- **验证**：`go test -race ./setting/... ./middleware/... -count=1`
- **回滚**：快照不影响 DB schema；回滚即恢复旧 getter。
- **风险**：低（读多写少，快照替换是标准做法）。
- **参考**：Go 官方 memory model（map 并发读写为未定义行为）；同类「启动期依赖 env 的共享对象」纪律见记忆台账 v1.3.50/51。

#### 4.2.3 长跑稳定性自检（P1 · 静态确认）

#### 4.2.6 【P1 · 静态确认】优雅关闭不排空 batch updater（停机丢额度增量）

- **缺陷**：`model/utils.go:35-42 InitBatchUpdater` 启动后**无 Stop/Flush 入口**（全仓无 `StopBatchUpdater`/`FlushBatchUpdate`）。停机路径 `main.go:245-260` 只做 `srv.Shutdown` → `model.StopConsumeLogFlusher()` →（条件）`SaveQuotaDataCache()`，**未 flush `batchUpdateStores`**。
- **入队点**：`model/user.go:1371-1379`、`model/token.go:412-416/441-445`、`model/quota_reserve.go:108-126`、`model/channel.go:947`。
- **后果**：生产 `BATCH_UPDATE_ENABLED=true` **已开启**（记忆·v1.3.67 确认）。停机丢最多 `BATCH_UPDATE_INTERVAL`（默认 5s，`common/init.go:118`）内的额度增量。方向是**平台少收**（上游已服务但未记账），**非计费安全不变式违反**；但属账务对账噪声。`docker rm -f`（SIGKILL）时窗口等于自上次 flush 起。
- **与日志 flusher 的不对称**：日志已专门实现排空（`main.go:252-254`），额度增量没有——同一类「内存缓冲 + 周期落库」只做了一半。
- **任务**：仿 `StopConsumeLogFlusher` 增加 `model.FlushBatchUpdate()`（加锁 swap 出 stores → 落库 → 返回错误）与 `model.StopBatchUpdater()`；在 `main.go:254` 之后、`SaveQuotaDataCache` 之前调用。
- **涉及文件**：`model/utils.go`、`main.go`。
- **验收**：新增用例「BatchUpdateEnabled=true → IncreaseUserQuota → FlushBatchUpdate → 断言 DB 已含增量」。
- **验证**：`go test ./model/ -run TestBatchUpdate -count=1`
- **回滚**：恢复不调用即可（行为回到旧版）。
- **风险**：低（与现有 flusher 同构；flush 失败仅告警，不阻断退出）。

#### 4.2.7 【P1 · 静态确认】后台 loop 未纳入优雅关闭

- **现状**：`main.go:241-254` 已做 `SetKeepAlivesEnabled(false)` → `Shutdown(timeout)` → `StopConsumeLogFlusher()`；`SHUTDOWN_TIMEOUT_SECONDS` 默认 120。

- **验收**：SIGTERM 后无「写库中进程退出」日志；本地 `kill -TERM` 观察。

- **风险**：中（涉及停机顺序，需真机验证）。

#### 4.2.8 【P2 · 实测确认】`idx_logs_traffic` 索引首列缺失且对聚合无收益

- **缺陷（实测 DDL + PRAGMA）**：`model/log.go:77-78` 的 `RequestBytes`/`ResponseBytes` 标注 `index:idx_logs_traffic,priority:2` 与 `priority:3`——**缺 `priority:1`**。对比同文件其他复合索引（`idx_created_at_id`/`idx_log_type_created_id`/`idx_log_user_type_created`）均完整含 `priority:1`，此项是**异常**。实测 AutoMigrate DDL：`CREATE INDEX idx_logs_traffic ON logs(request_bytes, response_bytes)`。
- **为何无收益**：站点总览/排行/流量统计的聚合是 `COALESCE(SUM(request_bytes),0)+COALESCE(SUM(response_bytes),0)`（`controller/log.go:251-256`、`:324`、`:388`）——**无 WHERE 谓词**，B-tree 索引完全不可用（全扫 + 回表）。索引只可能服务「某列等值查询」，但两者是字节数，现实无该谓词。且它让**每次日志 INSERT 多维护一棵索引树**（`model/log.go:109`、`consume_log_flusher.go:89`）。
- **注**：`计划书/db_structure.md:40,77` 将该索引记为「按流量」，与行为不符；perf-ledger 0012 的线上 EXPLAIN 清单**不含 logs 表 traffic 索引**，故此前未发现。
- **任务**：**直接删除该索引**（推荐；聚合无谓词，零收益只增写放大）。如确需加速聚合，正确手段是「按日预聚合表」（独立专项，本次不做）。
- **涉及文件**：`model/log.go:77-78`。
- **验收**：三库核对索引已删（`PRAGMA index_info` / `SHOW INDEX` / `pg_indexes`）；日志 INSERT 路径测试全绿。
- **验证**：`go test ./model/ -run TestDBConformance -count=1`（需 MySQL/PG）+ 幂等重跑；`计划书/db_structure.md` 同步更正。
- **回滚**：重新建索引即可（非破坏性）。
- **风险**：中（schema 变更，**必须三库验证**；GORM 默认不删多余索引，可能需显式 `Migrator().DropIndex`——需实测确认）。

### 4.9 v9.x 工程与治理（P1/P2）

#### 4.9.1 CORS 配置修正（P1 · 真实缺陷）

- **现状（实测证据）**：`middleware/cors.go:11` 设 `config.AllowAllOrigins = true`，`:12` 设 `config.AllowCredentials = true`——二者冲突。
- **为什么是缺陷**：二者语义冲突——`Access-Control-Allow-Origin: *` 与 `Access-Control-Allow-Credentials: true` 按 CORS 规范**不能共存**（浏览器会拒绝该组合）。经核对库源码 `gin-contrib/cors@v1.7.2/utils.go:21-22` 与 `:53-54`：当 `AllowAllOrigins=true` 时**无条件**写入 `Access-Control-Allow-Origin: *`，同时在 `:15` 写入 `Access-Control-Allow-Credentials: true`。结果：**依赖 Cookie 凭证的跨域请求实际被浏览器拦截**，而 `AllowCredentials` 从未生效。
- **影响面**：`router/api-router.go:301/372`（usage/log 路由）、`router/dashboard.go:15`、`router/relay-router.go:14`。本项目的会话刷新走 `SameSite=Strict` 的 refresh cookie（`service/auth_session.go:310`），主认证靠 `Authorization: Bearer`（header），**故生产主流程未受影响**——但任何依赖 Cookie 的跨域调用是坏的，且 `AllowCredentials=true` 是误导性死配置。
- **任务**：
  1. 明确 CORS 策略：若需 Cookie 凭证跨域 → 用 `AllowOriginFunc` 或显式 `AllowOrigins` 白名单（**不可** `AllowAllOrigins`）；若不需要凭证 → 移除 `AllowCredentials`。
  2. 生产环境应通过 env（如 `CORS_ALLOWED_ORIGINS`）控制白名单，默认仅同源。
  3. 复核是否所有 4 处挂载点都需要 CORS（relay 路由给第三方客户端调用，通常**不需要**浏览器 CORS）。
- **验收**：`AllowAllOrigins` 与 `AllowCredentials` 不再同时出现；浏览器跨域预检返回符合规范的头。
- **验证**：`go test ./middleware/ -run "CORS"`（需新增用例：断言响应头组合合法）+ 本地浏览器预检。
- **回滚**：还原 `middleware/cors.go`（行为等价，仅回退安全收紧）。
- **风险**：中（涉及跨域语义，需确认真实调用方是否依赖当前宽松策略；改前先 grep 前端是否有跨域场景）。

## 5. QA / 工程标准（横切所有主题）

### 5.1 RIPER-5 执行流程（每批强制）

1. **R 研究**：读现状证据 + 相关深挖文档 + 台账；分解需求、定位文件/符号、追踪链路；**严禁此阶段提方案/改码**。
2. **I 创新**：≥3 个方案（传统/优化/创新）+ 多维度评估（可行/成本/维护/性能/扩展/风险/可衍生/UI 可观性）+ 权衡矩阵；**不写实现细节**。
3. **P 规划**：选定方案 → 原子任务（目标文件/函数/变更/验收/风险）+ 执行顺序 + 质量检查点。
4. **E 执行**：严格按序 TDD；每步可测性验证；异常即停、记录、回退到稳定态。
5. **R 回顾**：成果验证（对照原始需求）、变更摘要、环境清理、质量报告、经验沉淀、归档 + 台账更新。

### 5.2 测试策略（务实守护关键路径）

- 计费/安全/三库不变量：单测锁定（`common/quota_math_test.go`、`relay/helper/openai_image_request_test.go`、`middleware/secure_verification_test.go`、`common/verification_test.go`、三库 conformance）。
- 前后端契约：契约测试 + 浏览器 E2E（HTTP + 真实浏览器双证）。
- 覆盖率：关键路径 ≥90%；不为数字写无断言测试；既有失败噪声按 §1.3 排除，不误判回归。
- 验收矩阵：每任务卡含「验证命令 + 证据路径」；未跑命令不声称通过。

### 5.3 证据与版本纪律

- 证据文件：`计划书/e2e-evidence/<类型>-<版本/日期>.{json,png,md}`。
- 每批结束：`VERSION` bump + `计划书/workflow_status.md` 新节 + `计划书/project_specs.md` + `graft build`。
- 提交：约定式（feat/fix/docs/test/perf/ci）；推送 main；tag + Release（沙箱受限时在 Actions UI 触发 `release.yml`）。
- **推 tag ≠ 已发版**：必须显式确认 GitHub Release 对象存在。

### 5.4 硬纪律（代价换来的，务必遵守）

**通用三条**：
1. **读 axios 错误码必须先读 `response.data.code`**，顶层 `code` 只在非 `ERR_` 前缀时采用。
2. **改 HTTP 状态码语义后，必须 grep 全仓断言旧状态码的测试**：`grep -rn "assert.Equal(t, 200" controller/*_test.go`。
3. **声称「测试全绿」前必须跑该包的全量测试**——定向 `-run` 通过 ≠ 包全量通过。

**并发与配置（§4.2 探针换来的）**：
4. **缺省同步原语必须做「成功路径 × 超时/取消路径」交叉测试**——并发桶泄漏正是因测试只覆盖独立路径、无交叉而潜伏。
5. **共享可变的配置/map，热更新必须快照替换（`atomic.Pointer`），禁止无锁就地写**——否则可触发不可 recover 的 fatal。
6. **「内存缓冲 + 周期落库」类组件必须在停机序列显式 flush**——日志 flusher 做了，额度 batch updater 没做。
7. **Go 1.23+ 的 `time.After` 不再泄漏计时器**——判缺陷前先核对 `go.mod` 版本。

**前端（§4.3 探针换来的）**：
8. **jsdom 下 axe 的 `color-contrast` 会落入 `incomplete` 而非 `violations`**——只断言 violations 的 a11y 测试是假绿；对比度须真实浏览器验证。
9. **`useState` 初值只算一次**——依赖异步就绪状态（如 auth `user`）的初值会冻结，须用 `useEffect` 重算。
10. **改前端后必须 `bun run build` 再重启 Go 服务**（`go:embed web/dist` 是编译期快照）。

## 附录 C：与 AGENTS.md 硬规则的对接清单（改每一项前必查）

| 改动类型 | 必查 |
|---|---|
| 计费/配额 | `pkg/billingexpr/expr.md`、`common/quota_math.go`、`types.PriceData.AddOtherRatio`、饱和审计 `attachQuotaSaturation` |
| JSON | `common.Marshal/Unmarshal/DecodeJson`（业务代码禁 `encoding/json` 直调） |
| relaykit | 独立模块约束；改动必须 `cd relaykit && GOWORK=off go build ./...` |
| 数据库 | 三库真实实例矩阵；迁移幂等；`lockForUpdate`；方言常量 |
| 认证/安全 | OWASP/ASVS（版本+requirement id）；审计去敏；服务端强制 |
| 前端 | `web/AGENTS.md` 复用优先；i18n；bun；typecheck |
| 外呼 | SSRF 校验（`service/url_guard.go`）；受控 URL 用 `common.NewOutboundClient`；禁止裸建 `&http.Client{}` |
| 文档 | 不新建 `docs/` 下文件除非用户要求；证据纪律 |
