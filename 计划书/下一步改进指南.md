### 1.3 CI 门禁真相 —— 本轮最重要的新发现（`已验证`，读 6 个 workflow 的触发条件）

**结论：本仓库 6 条前端门禁 + 后端 job，在你实际的工作流下从来没运行过。**

| workflow | 触发条件 | 是否跑测试/门禁 |
|---|---|---|
| `ci.yml` | **仅 `pull_request`**（opened/synchronize/closed） | 是（后端 vet/build/test + 前端 12 steps + 三库 conformance） |
| `release.yml` | `push: tags` | **否**，只构建三平台二进制并发布 |
| `docker-build.yml` | `push: branches: [main]`、`tags` | **否**，只构建多架构镜像 |
| `electron-build.yml` | `push: tags` | 否 |
| `sync-release-to-gitcode.yml` | release 事件 | 否 |
| 其它 | — | — |

而本仓库的实际发版方式是：**直接 `git push origin main` + 打 tag**（37 个提交、14 个 tag 全部如此，无 PR）。
两者相乘的直接后果：

1. `ci.yml` 里的 6 条门禁（术语 / 漏译 / 覆盖率 / 版本口径 / 令牌漂移 / knip）**一次都没跑过**；
2. 所以 §1.1 那条 RED 的版本门禁**没人被拦**；
3. 所以 `ci.yml` 里 `Test: bun run test` 这个**已知跑不完的步骤**也没人发现（见下）；
4. 所以「门禁」在本仓库目前只是一堆本地脚本，靠人记得跑。

**`ci.yml` 的 `Test` 步骤本身就是坏的**（`静态确认` + `已验证`）：

- `web/package.json` 里 `"test": "vitest run"`；
- `web/vitest.config.ts` 强制 `pool: 'threads'`、`maxWorkers: 1`、`fileParallelism: false`（这是为了修 `vmThreads` 下 `vi.mock` 串台，不能改回去）；
- 结果：单进程全量实测 **>25 分钟未跑完**（`test_ledger.md` 记录），而 frontend job `timeout-minutes: 10`；
- 已有的正解是 `web/scripts/test-shards.mjs`（`bun run test:shards`，5 片并行，历史 1582/1582 通过 567s），**但 CI 没用它**。

→ 这是一个**结构性假绿**：门禁写在 CI 里，看起来"我们有 CI"，实际既没触发、触发了也跑不完。

## 9. 方案对比与权衡矩阵

前提：D-2 已定**全部要做、不砍项**。所以方案比较的不是"做什么"，而是**排序与并行策略**。

### 方案 A — 运维保命优先（Ops-first）
先把 P0-1/P0-2 做完（备份 + 主机加固），代码轨道全部停一周。
- 优点：消除唯二能造成"不可恢复损失"的风险；成本极低（半天）；不碰产品代码。
- 缺点：**依赖外部条件**（SSH/授权），一旦拿不到就全线停摆；用户可感知改进为 0。
- 适合：你手上有 SSH 且愿意当天处理。

### 方案 B — 秤先校准（Gate-first）
先修 P0-3/P0-4（CI 加 push 触发 + 修红项），再跑 P1-1（三库）。
- 优点：**后续所有 PASS 才可信**；不需要任何外部条件；纯代码/配置；1 个版本可完成。
- 缺点：用户也感知不到；且"修门禁"本身容易变成自我循环（修门禁 → 发现更多红 → 继续修）。
- 适合：作为任何其他轨道的**前置批次**。

### 方案 C — 数据与钱优先（Correctness-first）
先做 P1-3（数据层性能 4 处）+ P1-4（计费 3 条）。
- 优点：直接减少 OOM 复发概率与资损；技术上最有含金量；证据链清晰（PG 慢查询 + 单测）。
- 缺点：改动触及 `model/` 与计费链路，**风险最高**（计费红线上次事故赔了 $20.86）；必须配三库验证（又依赖 B）。

### 方案 D — 欠账清零（Contract-first）
先清 B 轨道 7 张卡。
- 优点：用户最能感知；有尼尔森指南 42 条条款做验收依据。
- 缺点：**历史数据显示这 7 卡吃掉过 15 个版本才完成一半**；且 `zh.json` 是单文件共享，并行受限。
- 适合："产品要拿去给人看"的场景。

## 13. 质量门禁与证据要求

### 13.1 四级标签

| 标签 | 含义 | 允许出现在 |
|---|---|---|
| `已验证` | 本轮真实运行并观察到输出 | 可写 PASS |
| `静态确认` | 读代码/文件确认，未运行 | 只能写「静态确认」，**不得**写 PASS |
| `合理推断` | 有间接证据 | 必须同时写「缺哪一环」 |
| `待验证` | 缺环境/凭据 | 只能进「未验证项」 |

### 13.2 禁写 PASS 的六种情形（本项目历史事故复盘得出）

1. 没跑过命令就写「测试通过」。
2. 只跑了 `-run` 窄过滤，却宣称「全包 PASS」。
3. 用 mock 证明隔离逻辑，却描述成「真实集成已通过」。
4. 用「代码存在 / 有界面按钮」代替「用户路径走通」。
5. 断言只覆盖「没崩」。
6. 覆盖率数字达标但核心错误/边界/权限路径未测。

**本次新增第 7 条**：**门禁写在 CI 里但 CI 从不触发，不得写成"已有门禁保障"**。这是本轮发现的
最典型案例——`ci.yml` 里 6 条门禁 + 三库 job 看起来非常齐全，实际一次没跑（§1.3）。

### 13.3 每张卡完成时必须交出的六项证据

① 改动文件清单（`git diff --stat`）② 定向验证命令与**真实输出**③ 浏览器/接口证据路径（截图、JSON）
④ 回归范围说明（跑了什么、为什么不必跑更多）⑤ 回滚方式 ⑥ 未验证项与原因。
