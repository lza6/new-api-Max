2. 直觉（Why）——设计取舍

  • 500 是「网关自己坏了」，502 是「上游没接住」。网络层失败（connection refused / unexpected EOF）请求在 TCP/TLS 层就中断，从未到达上游应用——这解释了「上游没记录」。归为 500 会让用户误判为网关故障，也让监控无法把「真实 500」与「上游不可达」分开。改 502 + upstream_unreachable 语义准确；status>=500 仍命中 ErrClassServerError，渠道冷却/重试语义不变。
  • 超时 ≠ 不可达。isUpstreamUnreachable() 首行就把超时排除，超时仍单独走 504——两者可观测性不同（超时可能上游已在处理，不可达则保证未被处理）。
  • upstream_unreachable 绝不能降格。processChannelError 显式保留该分类，因为「请求未被处理、可安全重试」是关键信息，被 upstream_unavailable 覆盖就丢了。
  • 灾备用纯 Go 而不是 pg_dump。① 生产镜像是 debian-slim，容器内没有 pg_dump/mysqldump；② 引入外部二进制还要处理版本匹配与三库分支；③ 纯 Go + gzip + JSON Lines 流式写出，内存占用与表大小无关（生产 logs 50 万+ 行可安全导出），且 SQLite/MySQL/PostgreSQL 共用同一份 GORM 代码、无方言分支。
  • 导入语义选「只插入缺失行」而非「覆盖」。灾备文件最怕误导入把生产数据改坏。冲突跳过（clause.OnConflict{DoNothing:true}）意味着导入是幂等且可安全重放的，最坏情况是「没导入成功」，不会造成数据损坏。
  • 越权改 404 而不是 403。403 会泄露「该 id 存在但你没权限」，404 统一「不存在/无权限」，同时消除枚举面；单条与批量语义一致。
  • 首页用纯 CSS 3D 而不是 three.js。首页 LCP 预算敏感（web/performance.md 要求 App 页 JS < 300KB gzip），three.js 会显著拖慢首屏；perspective + rotateX/Y + translateZ 零 WebGL 依赖即可表达纵深。
  • 动画必须「渐进增强」。initial={false} + animate：默认可见、动画只作增强。JS/IO/动画失效时内容仍可读——这是把「可能永久空白」变成「最多没有动画」。
  • key 测试是只读诊断，不改健康分。测试失败若计入渠道健康评分，会导致「测试误伤生产渠道」；因此单测/批量测试都不触碰健康分（写进 plan AD-2）。

4. 上游 504 归因（重点）——为什么「上游没错误，我们有错误」

用户现象：用户看到 status_code=504 与 500 类错误，但到上游面板查不到任何失败记录，因此判断「不是上游的问题，是网关的问题」。

4.1 真实日志片段（生产）

dial tcp 70.39.183.88:443: connect: connection refused
unexpected EOF

4.2 真因

这两类错误的共同点是：失败发生在 TCP/TLS 层，HTTP 请求从未被送达到上游应用。上游服务根本没收到这个请求，因此上游侧留不下任何日志——这正是「上游没错误」的原因。问题出在网关的归类语义上：此前 doRequest 只区分「超时 → 504」与「其它 → 500」，网络层失败被塞进了 500。

把「上游不可达」报成 500 有两个实际危害：① 用户按 500 的字面含义（Internal Server Error）理解成「网关自己坏了」，产生误判与投诉；② 监控告警无法把网络层失败与真实网关故障分离。

4.3 修复后的分类

失败类型判定函数HTTP 状态错误码语义
上游总超时（如 RELAY_TIMEOUT）isRequestTimeout()504do_request_failed（"upstream request timed out"）上游可能已在处理，语义与不可达不同
连接被拒 / 网络不可达 / TLS 或连接中途断开 / DNS 失败isUpstreamUnreachable()502upstream_unreachable请求从未到达上游应用 → 上游无记录、保证未被处理、可安全重试
其它 client.Do 失败—500do_request_failed兜底

识别覆盖三类：① connection refused / no route to host；② io.EOF / ErrUnexpectedEOF / ECONNRESET；③ DNS no such host。因 Go 的 http 包在连接中途断开时常返回未包装的字符串错误（errors.Is 匹配不到），额外做了一层关键字兜底判定——该兜底只在网络层分支使用，不会误判业务错误。

summarizeNetworkError() 把底层错误压成一句可读短句（如 connection refused / connection closed by upstream / dns resolution failed），避免把完整 URL 与 Dial 细节透给终端用户，同时保留可诊断信息。

另外 processChannelError 显式保留 upstream_unreachable，不被降格为笼统的 upstream_unavailable——后者会丢掉「请求保证未被处理、可安全重试」这一关键信息。

回归防护：TestIsUpstreamUnreachable（relay/channel/api_request_getbody_test.go:639，含「超时/业务错误不得误判」）、TestSummarizeNetworkError（:663）、TestProcessChannelErrorPreservesUnreachableClass（controller/relay_error_log_test.go:479）。

5. 数据库导出 / 导入（灾备）

维度设计理由
实现方式纯 Go，不依赖容器内的 pg_dump/mysqldump生产镜像是 debian-slim，容器内没有这些二进制；引入外部工具还要处理版本匹配与三库分支
文件格式gzip + JSON Lines 流式：首行 BackupMeta（kind / version / created_at / app_version / db_type / include_logs），每个表段前一行 {"__table__":"...","count":N}，随后逐行一条 JSON内存占用与表大小无关，生产 logs 50 万+ 行可安全导出；三库共用同一份 GORM 代码，无方言分支
导入语义只插入缺失行（主键冲突跳过），绝不删除或覆盖已有数据；返回 inserted / skipped冲突跳过使导入幂等、可安全重放；最坏情况是「没导入成功」，不会损坏生产数据
防错格式版本校验（meta.Version > backupFormatVersion 明确拒绝并提示升级）、单行 16MiB 上限（maxImportLineBytes = 16 << 20）、请求体 1GiB 上限、未知表段跳过其数据行、无法解析的行计入 errors畸形/恶意/未来版本文件不能造成内存爆掉或误写
导入后处理RefreshRuntimeStateAfterImport() 刷新 option / 渠道 / 定价缓存避免进程内缓存仍是导入前的旧状态
单一样本来源model.BackupTables() / model.LogTables()改 AutoMigrate 时必须同步，避免导出漏表

测试：service/db_backup_test.go —— 往返 + 幂等重放、非本格式拒绝、未来版本拒绝。

6. 独立审查循环（本批亮点）

两轮独立审查累计报出 6 个真实缺陷，每个都先实测复现再修——不接受「看起来应该有问题」的推断，也不接受「看起来应该修好了」的声明。

6.1 C-1：整段回退逻辑是死代码（真实 axios 复现）

根因：readServerCode() 先读 error.code。但 axios 对所有 4xx/5xx 都会把 error.code 设成 ERR_BAD_REQUEST / ERR_BAD_RESPONSE 这类传输层标识，业务 code 只存在于 response.data.code。顺序写反 → SECURITY_PROOF_REQUIRED 永远读不到 → 「站点强制验证时弹窗重试」的整条路径永远不会执行。

为什么此前没被发现：旧测试用 new Error()（不带 code 字段）伪造错误，恰好绕过了该缺陷——属假阳性测试。审查用真实 axios 形状复现后，测试同步改用带 code:'ERR_BAD_REQUEST' 的真实形状。

// 真实 axios 形状（回归用例构造，web/src/features/keys/hooks/__tests__/token-key-disclosure.test.tsx:107）
function proofRequiredError() {
  return Object.assign(new Error('需要安全验证'), {
    code: 'ERR_BAD_REQUEST',          // ← axios 实际会设置这个值
    isAxiosError: true,
    response: {
      status: 403,
      data: { success: false, code: 'SECURITY_PROOF_REQUIRED', message: '需要安全验证' },
    },
  })
}

6.5 本次沉淀的纪律

  1. 读 axios 错误码必须先读 response.data.code，并排除 ERR_ 前缀的传输层码；测试必须用真实 axios 形状（带 code:'ERR_BAD_REQUEST'），否则造出假阳性。
  2. 新增 i18n.T 调用前，先确认测试链路已 i18n.Init()；i18n.Translate 现已有 nil-bundle 保护，但测试仍应显式 Init 以贴近生产。
  3. 改 HTTP 状态码语义后，必须 grep 全仓断言旧状态码的测试（grep -rn "assert.Equal(t, 200" controller/*_test.go）。
  4. 声称「全绿」前必须跑该包的全量测试 —— 定向 -run 通过 ≠ 包全量通过（P0-A 正是这么漏掉的）。
  5. 改「验证/弹窗」类前端逻辑后，必须 grep 全仓所有断言旧流程的测试（grep -rn "step-up\|Verify to view" web/src --include=*test*）。
  6. 组件改图标按钮时必须带 aria-label（axe button-name 为 critical）。
  7. 起本地 E2E 服务必须先 bun run build 再重启 Go（go:embed web/dist 是编译期快照，只改前端不重启 = 白测）。
