1. 上下文（Context）——解决什么

指南 §4.1.1「热路径缓存」原任务卡假设「用户设置/定价快照每请求多次读库，需加缓存」。**审计（证据优先）推翻该前提**：用户（Redis+AuthVersion 栅栏）、token（Redis）、渠道（运行时快照）、计费（内存）、定价（1min 缓存 + 变更失效）均已有缓存，中继热路径零直接 DB 调用——**不重复造轮子**。

**真·缺口**：限流中间件对「有 active 订阅」用户，每个中继请求执行一次 GetAllActiveUserSubscriptions DB 查询（无订阅用户已有 15s 负缓存）。订阅用户通常是 API 高频调用方 → 每请求一次 DB 往返是真实热点。

2. 直觉 / 动机（Why）——设计取舍

  • 只缓存软限，绝不缓存计费：缓存对象 = 「active 订阅摘要」用于限流档位（EffectiveTier：并发/RPM）。NewBillingSession 的 HasActiveUserSubscription/AllowWalletOverflow、PreConsumeUserSubscription 保持 DB 权威——避免任何记账/回退方向的秒级偏差。
  • 变更写后失效 > 只靠 TTL：在订阅创建/作废/删除/重置/到期降级/过期 6 处失效（model 内，无 model→service 环）；v1.3.48 补上「档位覆盖 PATCH」失效。秒级滞后对软限可接受，但失效让它几乎为 0。
  • 开关可回滚：env SUBSCRIPTION_ACTIVE_CACHE_SECONDS，默认 10s、0=关闭（逐位回退基线）。
  • 容量有界：上限 20000 条目，达上限先清过期、仍达上限随机删至一半（保留热点，非整表清空）。
  • 多实例口径：进程内缓存，与既有 no-subscription 负缓存、RPM 计数同口径（已文档注明）。
