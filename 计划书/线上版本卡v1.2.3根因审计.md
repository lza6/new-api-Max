# 线上版本卡在 v1.2.3 根因审计（2026-09-19）

## 结论
线上 `freeapi.tingfengai.art` 显示的 v1.2.3 **是真实的**，且部署链路有 3 个环节断裂：

1. **GitHub Actions 的 `push: tags` 触发器从未生效**：全部 22 次 workflow run 都是手动
   `workflow_dispatch`，`event=push` 的 run 数 = 0。GitHub events API 也显示所有 push
   都是 `refs/heads/main`，**没有任何 `refs/tags/*` 的 push**。
2. **因此 v1.2.4 → v1.2.16 的 tag 从未构建成镜像**：
   `ghcr.io/lza6/new-api-max:v1.2.16` → `not found`（已实测验证）。
3. **线上跑的是 9/13 手动构建的 v1.2.3 镜像**：
   - 最后一次手动构建 run 34733377645 的 `head_sha = 2ac497822…`，恰为 v1.2.3 的 commit
   - 新版 `latest` 从未出现 → watchtower 每天扫描（Scanned=4 Updated=0）自然永远更新不了

## 关于"热更新热重启"
- watchtower 存在且运行正常（每天 22:13 扫描），但它只在 ** 镜像 digest 变化 ** 时才更新容器
- 因为 GHCR latest 从未更新，watchtower 无活可干 → 用户感知为"没有热更新"
- 真正缺口：CI 自动化断裂（tag push 不构建），不是 watchtower 的问题

## 版本号机制
- `common/constants.go: Version = "v0.0.0"`（占位）
- Dockerfile: `go build -ldflags "-X ...common.Version=$(cat VERSION)"`
- CI 在构建前 `echo "${TAG}" > VERSION` → 镜像内版本 = 构建时 tag
- 运行时也可 `VERSION` 环境变量覆盖（common/init.go:35）
