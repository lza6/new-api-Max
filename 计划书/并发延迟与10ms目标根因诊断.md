# 并发延迟与「10ms 附加延迟」根因诊断（实证，2026-09-20）

## 1. 用户问题
- 2C2G 服务器透传路由，理论上 120 并发/s 没问题，但并发一上来延迟暴涨；
- 目标：网关附加延迟 ≤10ms；
- 上游没报错（含工具调用）我们却报 400/500 的偶发疑问。

## 2. 实证基准（本地 v1.2.33 网关 + 0 延迟本地上游，真实 HTTP）
证据：`计划书/e2e-evidence/latency-bench-v1.2.33.json`
| 并发 | 直连 p50/p95 (ms) | 网关 p50/p95 (ms) | 网关附加 p50/p95 (ms) |
|---|---|---|---|
| 1 | 69.8 / 71.6 | 83.8 / 99.6 | 14.0 / 28.0 |
| 20 | 83.7 / 91.7 | 242.1 / 380.4 | 158.4 / 288.7 |
| 50 | 84.1 / 96.5 | 150.2 / 334.8 | 66.1 / 238.2 |

直连曲线平坦（mock 本身 ~70-96ms，含流式分片），**网关并发附加延迟 66-289ms**。

## 3. 根因（日志实锤）
- 网关日志出现 **SLOW SQL ≥200ms：INSERT INTO logs ... 241ms**；
- 每个请求在返回前**同步写一条 consume log**（model/log.go RecordConsumeLog → INSERT logs），SQLite 单写者 + WAL 下高并发产生**写锁串行化与排队**；
- 叠加：Token 鉴权 DB 读（本地无 Redis）、option/channel 5s 同步、GC/CPU 争抢（2C）；
- 生产若日志库与主库同库（未配 LOG_SQL_DSN）或为 SQLite，同样被同步写拖慢；配了 PG 也仍是每请求一次同步 INSERT。

→ 结论：**不是透传/缓冲问题（透传零缓冲已被 E2E 证明），是热路径同步落库**。与 sub2api「用量/日志异步 flusher」的差距一致。

## 4. 达成 ≤10ms 的修复设计（按影响排序，均需落地后复测）
1. **异步 consume-log 落库（核心）**：请求路径把日志写入内存队列/环形缓冲（O(1)），后台批量 flush（默认 5s/500 条，退出时 flush）。请求返回不再等 INSERT。
   - 权衡：进程崩溃最多丢一个批次日志（可接受；WAL 保证已提交数据）；计费流水仍同步（不动机器/账务）。
   - 实现点：`model/log.go RecordConsumeLog/RecordErrorLog` 入口 + 新 `service/log_flusher.go`（队列+worker+关闭 flush）；env `LOG_FLUSH_INTERVAL`/`LOG_FLUSH_BATCH`，默认开。
2. **Token 鉴权缓存**：本地无 Redis 时 DB 读 ~1-5ms；生产已用 Redis。保持。
3. **连接池收敛**：`SQL_MAX_OPEN_CONNS` 1000→64（2C 机 PG 上限），降争用。
4. **日志库独立/ClickHouse**（已有 LOG_SQL_DSN 选项）：写放大远离主库。

## 5. 429 / 工具调用 / 400-500（现状与方案）
- 429：`service/relay_error_class.go ClassifyHTTPStatus` 已按 aisix 模型给出 retryable/cooldown；`stream_scanner.go` 已实现空流/仅 reasoning 判失败并交还重试链（对齐 free-router）。**缺口：429 未做「等 1s 后有界重试」** → 方案：relay 层对 429（及 Retry-After 更大者）等待后重试同一请求（默认 1 次、可关 env `RELAY_429_RETRY_DELAY`/`RELAY_429_MAX_RETRIES`），请求体可重放（ReplayableBody 已具备）；仅限 chat 类幂等场景，留审计。
- 工具调用/400/500：既有诊断证明 400 = 上游真实拒绝透传；空壳流已 failover。后续若再现"上游 200 我们报错"，按 `other.stream_status`/`frt`/`usage_billing_path` 三字段定位到具体转换点再修。

## 6. 流量统计（T4 方案）
- 每请求字节：请求体 `ReplayableBody` 已有 size；响应字节在流拷贝/JSON 写处累加 → 写入 consume log `other.request_bytes/response_bytes`。
- 聚合：新端点 `GET /api/logs/traffic?days=1|7|30`（SUM bytes GROUP BY day），前端 usage-logs 顶部加「流量卡」（今日/7日/30日 MB + 实时），并修正 RPM 显示口径（现有 rpm=最近 60s count，UI 若按分钟换算需核对）。
