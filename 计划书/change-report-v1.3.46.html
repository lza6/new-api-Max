commit 7d6d2888（+ 终局审计补位 commit）· 分支 main · 2026-09-27 · 批：T8-G1/G4/G5 + T15-A/B/C + 审计补位

1. 上下文（Context）——这次在解决什么

仓库 计划书/docs/（T1–T15 深挖文档）此前仍有三类开放项：T8 安全 Gap（G1 API Key 明文查看无 step-up、G4 邮箱枚举、G5 验证码内存存储）与 T15 立项未实施（A 订阅站点统计、B 通用 webhook、C 公开定价）。生产实例已在使用，要求全部真实落地闭环 + 真实 E2E + 审计 + 交付（提交/推送/发行版）。

为什么危险：G1 意味着拿到会话的攻击者可静默窃取明文 API Key；G4 让攻击者可枚举注册邮箱；G5 让多实例下验证码失效/可重放；T15 三项是「写了文档没实现」的伪闭环风险。

2. 直觉 / 动机（Why）——设计取舍

  • G1 复用既有安全验证框架（`service/security_verification.go` 的 scope/proof/一次性消费/上下文哈希），新增 `token.key.read` scope，而不是另起炉灶 —— 与 channel.key.read 完全同构，风险最低。
  • G4 统一响应而非隐藏接口 —— 防枚举的标准做法：响应逐字节一致，已注册邮箱不落码不发信，发送失败仅日志（避免响应差异泄露状态）。
  • G5 Redis 优先 + 内存兜底 —— 解决多实例验证码不一致（内存 map 是每实例独立），且 Redis 不可用时行为与旧版完全一致（无回归）。一次性消费用 Lua 原子「匹配才删」。
  • T15-B 复用既有 event bus + SSRF 守卫 —— webhook 只做「通知+签名+幂等」，不参与结算（守住 t15 反范围蔓延护栏）；顺带补上了此前未定义的 `SendWebhookNotify`（用户级通知的隐藏缺口）。
  • T15-A 只读聚合、零新增表 —— 公开端点只回计数（无用户/订单字段），三库 GORM 兼容。
  • 审计补位 —— 反向审判发现 5 个自证缺陷（task.settled 只覆盖批次、chat 取消死循环、webhook 保存不查 SSRF、Redis TTL=0 永不过期、批量复制>100 静默失败），全部修复并回归。
