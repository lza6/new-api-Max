# §4.3.3 B 端与增长观测（P3）· 落档建议

> 状态：**落档建议，本轮不实现** | 日期：2026-09-28 | 批次：v1.3.57（005）
> 依据指南护栏：一次只做一个方向；不做自动涨价/自动风控闭环。

## 背景
P1（定价透明）与 P2（留存续费）已在本批实现。P3 三个方向属于增长/企业级观测能力，
单独成方向、复杂度高、依赖面广，按护栏落档为建议供治理层选择，不占用本批实现。

## 方向 1：API 用量/成本报表导出（企业审计角度）
- **目标用户**：B 端客户/企业管理员，需要按租户/按渠道/按模型维度的用量与成本导出。
- **现状基础**：
  - `logs` 表记录每次请求（用户/渠道/模型/token/用量/成本），`GetAllLogs` 已有分页查询。
  - 订阅/余额计费维度已有（billing 会话、quota 记录）。
  - 无「报表聚合/导出」端点（CSV/Excel），无按时间窗聚合查询。
- **实现思路**：
  1. 新增聚合端点（如 `GET /api/logs/report?group_by=model|channel|day&start=&end=`）：SQL 按维度 GROUP BY + SUM（用 GORM 或 raw SQL，三库兼容注意方言）。
  2. 导出格式 CSV（占内存可控，流式写）或 Excel（引入库成本高，先 CSV）。
  3. 权限：admin + 可选企业租户维度（若有多租户隔离需求另行设计）。
- **依赖**：`model/log.go` 聚合查询；`controller` 报表端点；前端报表页（可复用 data-table）。
- **优先级建议**：P2（企业客户进线主要诉求是账单可审计）。

## 方向 2：邀请/分销（aff_code 已有基础）
- **目标用户**：平台运营者；现有用户裂变增长。
- **现状基础**：
  - `aff_code` 已有基础：用户可生成邀请码（`/api/aff` 相关，wallet/api.ts 有 AffiliateCodeResponse/AffiliateTransferRequest）。
  - 邀请来源已在注册页/详情展示。
- **实现思路**：
  1. 邀请码 → 新用户注册绑定归属（aff_code 落库，已有部分）；注册成功给邀请人返佣 quota（管理员配置比例）。
  2. 邀请数/贡献看板（邀请人侧展示邀请列表、注册数、返佣记录）。
  3. 防滥用：同 IP 批量注册检测、返佣上限、风控开关（护栏：不自动闭环，手工风控）。
- **依赖**：现有 aff_code 模型；`model/affiliate*` 扩展；前端 my-invite 页。
- **优先级建议**：P2（增长杠杆明显，但需防滥用设计先行）。

## 方向 3：公开站点统计扩展为增长看板
- **目标用户**：运营者。
- **现状基础**：
  - T15-A 已落地公开订阅统计（`/v1/stats/subscriptions` 聚合计数，无明细泄露）。
  - 前端已有 `SiteSubscriptionStatsCard`（定价页展示）。
- **实现思路**：
  1. 增长看板数据源扩展：日/周激活、注册趋势、活跃渠道数（只暴露聚合，不泄露用户明细——沿用 T15-A 隐私边界）。
  2. 前端独立看板页（或 dashboard 子 Tab），图表用既有 vchart。
  3. 缓存沿用 stats 短缓存模式（ENV 可调）。
- **依赖**：`model` 聚合查询扩展；前端看板页。
- **优先级建议**：P2。

## 护栏（必须遵守）
1. **一次只做一个方向**：从上述三方向中选一版启动（建议方向 2 或 1），未批准前不并行铺开。
2. **不做自动涨价**：任何价格/额度变更必须管理员显式操作，不做自动调价闭环。
3. **不做自动风控闭环**：滥用检测只告警人工处置，不做自动封禁/自动降级。
4. **隐私边界**：公开统计只暴露聚合计数，不泄露任何用户/渠道明细（延续 T15-A 设计）。

## 下一步建议
- 若要启动 P3，建议先做方向 2（邀请分销，增长价值最高且 aff_code 基础已有），立项后按 Spec-Kit 建 006 条目。
- 方向 1（报表导出）可作为企业客户售前配套，视客户进线需求排期。
- 方向 3（增长看板）可与 dashboard 现有工作区衔接，工作量最小。
