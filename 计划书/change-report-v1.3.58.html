main · 2026-09-29 · 事故根因已用生产时间戳对齐证实 · 修复含 3 处后端 + 2 处前端 + 5 个回归测试

1. 上下文（Context）

用户报告线上近 100 条错误 + 「复制密钥有问题」+ 「访问网站偶尔 500/503」。排查发现 Caddy 24h 内 no upstreams available 503 共 1093 次，网关 rate limit check failed 280 次（其中 246 次直接转 500），Redis OOM command not allowed 434 次且仍在持续。

2. 直觉（Why）——事故链与设计取舍

  • 触发：管理员打开 /usage-logs/common → 前端 getLogsTraffic(30) → GET /api/log/traffic?days=30（实测 27-45s）。
  • 写爆 Redis：handler 把 30 天窗口内全量 442,661 行日志的 other JSON（291MB）整体 marshal 后 RedisSet，而 Redis maxmemory 仅 48MB。
  • 内存顶格：used_memory_peak 769.97M；redis 容器 cgroup peak 100663296（顶满 mem_limit 96m）→ 返回 OOM → 主线程阻塞。
  • fail-closed 放大：限流 Lua EVAL 全挂 → middleware/rate-limit.go 把 Redis 错误直接转 500（近 24h 246 次）。
  • 上游被摘：/api/status >2s → Caddy health_timeout 2s / health_fails 3 判死唯一上游 → no upstreams available 503 × 1093。
  • 时间戳铁证：07:32:02-07 的 16 次 OOM ↔ 07:32:07 traffic 完成；07:36 / 07:49 / 07:52 / 07:53 四轮全部重合。
  • 取舍：限流降级保留限流效果（内存桶参数与 Redis 桶一致）而非直接放行——宁可跨实例精度下降，也不把一次缓存故障放大成全站 5xx。

4. 归因结论：渠道 46 的三条 400 是上游问题

用户提供的三条报错，逐条核实全部来自上游 api.kabuai.cn，本网关只做透传 + 记录：

报错文案归因证据

间歇性证据：同一 payload 连打 10 次，第 9 次才 400（run1-8 ok / run9 REJECTED / run10 ok）→ 上游多实例配置不一致。另：上游 request-id 前缀 8268d9f6 ≠ 本仓构建前缀 fd097e04，佐证上游是另一套 new-api 中转。
