# ADR-003：压缩必须先按行切分、再逐块 gzip

> 目录：`计划书/adr/`（编号在本目录内独立）。本次决策批次：训练数据采集 Spec-008。
> 最后核对：2026-10-16（`VERSION` = `v1.3.147`）。

## 背景

用户要求大文本「压缩完再上传」，而不是单条 64KB 截断（`service/training_capture/compression.go:9-25`）。
云盘（OneDrive）单次简单上传有 4MB 上限，所以压缩后仍需分片。

这是一个**真实踩过的数据损坏级 bug**：最初实现是**先对整个 payload 做一次 gzip**，
再把压缩产物按字节切开。结果每个分片是一个 gzip member 的**碎片**，不是合法 gzip
（`unexpected EOF` / `invalid header`）。后果不是报错而是**静默乱码**——预览按 gzip magic 判断失败后
把二进制垃圾当明文显示，分析端把碎片当明文喂给模型（`service/training_capture/worker.go:465-478`）。

## 决策

**顺序硬约束：先按原始 JSONL 的「行边界」切分，再对每一块独立 gzip。**
每个分片因此是一个**完整、可独立解压的 gzip member**（`worker.go:479-488`）。

配套不变量（写在预算派生里）：**单分片原始上限 ≥ 单条文本上限 × 8**
（`resources.go:197-209`）。理由：分片按行切，但一条记录本身超限时只能硬切，会把一条 JSON 记录
切成两半，云盘上的 JSONL 再也无法逐行解析（数据集损坏且不报错）。JSON 转义最坏放大 ~6 倍，
取 8 倍留余量，保证任何通过文本上限的记录其 JSON 编码后仍能整条放进一个分片。

## 被拒绝的替代方案

1. **先整体 gzip 再按字节切**（原始做法）：产出坏 gzip 碎片 → 静默乱码（见背景）。
   已用 RED 验证：改回旧序 → 测试打印出泄漏的 gzip 魔数。
2. **不压缩，只靠截断**：用户明确否决（二三十 MB 的对话应压缩上传而非丢弃）。
3. **解压时不设上限**：gzip 解压比可 >1000:1，恶意文件可 OOM；故加 `io.LimitReader` 防 zip-bomb
   （`compression.go:56-73,79-81`）。

## 后果（含代价）

- ✅ 每个分片可独立解压，消费方（训练管线 / 管理端分析）契约明确：文件名后缀 `.jsonl.gz` 即声明
  （`compression.go:21-25`）。
- ✅ 压缩率实测 ~1/5，单分片承载 20~40MB 原始对话，上行带宽降一个量级。
- ⚠️ 用 `gzip.BestSpeed`（非最高档）：压缩在 worker goroutine，30MB 文本用 `BestCompression` 要
  数百毫秒到秒级、期间 worker 无法消费队列，积压会放大丢弃率（`compression.go:29-32`）。
- ⚠️ 压缩后仍可能超 4MB（已压缩内容/随机数据）→ 需**再切一刀**并各自重压，而不是硬塞（`worker.go:495-511`）。
- ⚠️ 压缩失败降级为**明文上传**（宁可多占带宽不丢数据）并记日志（`worker.go:490-494`）。
