## 1. 带反向锁的回归测试 —— `controller/spa_seo_test.go:233-263`

**本项目最痛的教训是「CI 全绿但线上坏」。** 这个用例是治它的标准解法。

```go
// og:url 必须是**结构完整**的 meta 标签，且指向本页的绝对地址。
// ...当时的断言只检查 og:locale 是否存在，所以 CI 全绿而线上是坏的 ——
// 断言"某标签存在"不等于断言"标签仍然合法"。
func TestSPASEOSetsWellFormedOGURL(t *testing.T) {
	// ...
	assert.Contains(t, page, `<meta property="og:url" content="`+want+`" />`, ...)

	// 反向锁：替换串写坏时会留下 `X content=`。这条断言让它无从遁形。
	assert.NotContains(t, page, `X content=`, "og:url 替换串写坏了（出现 X content=）")
	// ...
}
```

**为什么这是好例子**

1. **它锁的是「结构完整」，不只是「标签存在」。** 旧断言只查 `og:locale` 是否存在，
   而 og:locale 是**拼接追加**的，所以「标签被写坏」这件事没有任何断言覆盖 ——
   缺陷正是从这个盲区上线的（`controller/spa_seo_test.go:235-238`）。
2. **反向锁（negative assertion）让它无从遁形**：`NotContains "X content="`
   精确命中那个「漏写开头」的错误形态。正向断言只说「应该有」，
   反向断言才说「不许有坏的痕迹」。
3. **它还断言了两个字段之间的一致性**：og:url 与 canonical 必须指向同一个地址，
   否则分享卡片与收录指向会分叉（`controller/spa_seo_test.go:258-261`）。
   跨字段一致性往往比单字段存在性更能抓住真实缺陷。
4. **注释里写清了事故经过**，所以后人能判断「这条锁还在不在保护一个真实风险」，
   不会当作冗余断言删掉。

**配套纪律**：写完后做 **RED 反向验证** —— 把 bug 放回去，确认用例**真的会 FAIL**
（且错误信息精确指向问题），再恢复。`计划书/workflow_status.md:567` 记录了这条流程。

## 2. 带反向锁的回归测试（第二条）—— `controller/task_generic_test.go:601-668`

```go
// Batch-13 / G6-5：产物文件在 Resolve 与 Serve 之间被清理时，**不得**返回 200 空体。
//
// 锁的是一个真实缺陷（`controller/task.go`）：原实现是
//     _ = artifactStore.Serve(c, task, ref)
//     return
// ...
// 关键断言是**响应体非空**：回退到上游代理后返回 200 + 真实内容是正确行为，
// 缺陷是「200 + 空体」。因此不能断言状态码不是 200（那会误伤正常的代理响应）。
```

**为什么这是好例子**

1. **断言选得准**：缺陷是「200 + 空体」，而正确行为**也是 200**。所以断言
   `assert.NotEmpty(body)` 而不是 `assert.NotEqual(200, code)` ——
   后者会误伤正常的代理响应（`controller/task_generic_test.go:663-667`）。
   **断言必须对准缺陷本身，而不是它的表面现象。**
2. **它正面构造了那条难测的竞态分支**：用 `service.SetTaskArtifactStoreForTest`
   注入一个「已启用、能 Resolve、但 Serve 时文件已不在」的 store
   （`controller/task_generic_test.go:645-650`）。
   这条分支在真实环境下**只能靠运气撞到**，所以项目专门为它开了测试注入点
   （`service/task_artifact_store.go:55-65` 的注释解释了为什么必须有这个点）。
3. **它验证的是「回退真的发生了」**：用一个返回标记内容 `upstream-fallback` 的
   `httptest.Server` 作上游，断言响应体**等于**那个标记
   （`controller/task_generic_test.go:619-623,666`）——不是「没报错」，
   而是「确实走了另一条路径」。

## 3. 有界登记表 —— `common/loop_heartbeat.go:27-69`

```go
// loopHeartbeatMaxEntries 是登记表条目**硬上界**。
//
// 上面的「name 必须是编译期常量」是约定；这里把它变成**被强制的**上界：
// 超过则拒绝登记并告警一次。这样即便将来有人误把业务键（如用户 ID）传进来，
// 也不会把这张表变成新的无界增长点 —— 本批次修的正是这一类问题。
const loopHeartbeatMaxEntries = 128
```

**为什么这是好例子**

1. **把「约定」升级为「被强制的上界」。** 注释说得非常清楚：靠「大家都传常量」
   只是约定，靠 `if len(m) >= max { 拒绝 + 告警 }` 才是保证（`common/loop_heartbeat.go:60-65`）。
   这是本项目对「无界增长」这类问题的标准应答方式。
2. **拒绝而不是静默丢弃**：超出上界时用 `CompareAndSwap` **只告警一次**
   （`common/loop_heartbeat.go:61-63`），既不刷爆日志，也不让问题隐身。
3. **上界被暴露给测试**：`LoopHeartbeatMaxEntries()`（`common/loop_heartbeat.go:37`）
   让测试能断言这个数字，而不是把常量散在断言里。
4. **设计前先算过增长源**：注释明确「键是编译期常量，条目数 = 接入的 loop 数量，
   有界且不随流量变化」，并解释了**为什么**因此刻意用「调用方传固定字符串」
   而不是「按业务键登记」（`common/loop_heartbeat.go:17-18`）。

## 4. 外部输入驱动的标签必须有界 —— `common/metrics.go:51-58,63-104`

```go
// maxMetricLabelSeries 是**单个**指标名允许的最大时间序列（标签组合）数。
// 超出后新组合不再新建序列，转而累加 `<name>_label_series_overflow_total`（无标签）。
//
// 为什么必须有：只要标签值里有一个来自**外部输入**，攻击者就能用天文数字个不同值把
// 计数器 map 撑爆 —— 最典型的就是 HTTP method（Gin 会原样接受请求行里的任意 token）。
```

**为什么这是好例子**

1. **它识别出「标签值来自 request line」这个攻击面**：`middleware/logger.go:54-58` 把
   `param.Method` 直接交给 `NormalizeHTTPMethodLabel` 后写入 —— 任意 token 都算一种 method，
   标签组合**无界且无淘汰**（`计划书/workflow_status.md:242`）。**先定位增长源，再设计边界。**
2. **双层修复，缺一不可**：
   - ① `NormalizeHTTPMethodLabel` 把方法**归一化到有限集合**（未知 → `OTHER`），
     既保住「有人在发怪方法」这条可观测量，又不让标签空间随外部输入膨胀
     （`common/metrics.go:63-75`）；
   - ② `MetricsInc` 再加 `maxMetricLabelSeries` 硬上界兜底，防止将来别处再引入
     外部输入标签（`common/metrics.go:93-102`）。
   归一化是「治本」，硬上界是「不管谁写错都不炸」。
3. **溢出时**不静默丢**：超限样本计入 `<name>_label_series_overflow_total`
   （`common/metrics.go:94-101`）——**既不丢可见性，又有硬上界**的折中。
4. **反向锁住了溢出计数器**：`TestMetricsIncCapsSeriesCount` 的 RED 验证里，
   短路序列上限判断会得到 `"6000" is not less than or equal to "2000"` 与
   `"0" is not positive`（`计划书/workflow_status.md:224-229`）。

## 5. 进程内 LRU：硬容量上界且不常驻 goroutine —— `service/response_cache.go:69-89`

```go
// responseCacheLRU 是带 TTL 的进程内 LRU。
//
// 为什么要 LRU 而不是普通 map：内存必须有**硬上界**（用户关切的无界增长问题）。
// 容量由 `response_cache_setting.MaxEntries()` 决定；每次写入淘汰最旧一条；
// 读取时顺带做过期判定。**没有后台 goroutine** —— 清扫在写入路径上分批做，
// 避免为一个小功能常驻一个 ticker。
```

**为什么这是好例子**

1. **「没有后台 goroutine」是主动的设计决策，不是偷懒**：注释给出了理由 ——
   避免为一个小功能常驻 ticker。常驻 ticker 本身就是一类常见的泄漏源
   （见 §3 的 loop 心跳就是为了观测它们）。**取舍写清楚，后人不会「顺手」加回去。**
2. **两个维度都有界**：容量（LRU 淘汰）+ 时间（TTL 过期判定），
   且**清扫在写入路径上分批做**（`responseCacheSweepEvery = 256`，
   `service/response_cache.go:88-89`）——避免「清扫本身变成一次长阻塞」。
3. **上界可配但有顶**：`MaxEntries` 默认 1000、上限 20000
   （`setting/response_cache_setting/response_cache_setting.go:27-29`），
   管理员配不出「无界」。

## 6. 有界读取，且超限报错而不静默截断 —— `common/read_limit.go:9-63`

```go
// 纪律：超限必须返回**明确错误**，绝不静默截断 —— 截断的上游 JSON 会变成
// 难排查的解析错误，比直接报「响应过大」糟得多。
	...
	data, err := io.ReadAll(io.LimitReader(r, maxBytes+1))
	...
	if int64(len(data)) > maxBytes {
		return nil, fmt.Errorf("%w: limit=%d bytes", ErrReadAllLimitExceeded, maxBytes)
	}
```

**为什么这是好例子**

1. **把「我们不完全信任上游」写成代码约束**：注释点明上游异常/恶意响应能让单进程
   把内存吃穿（生产只有 4GB），这就是为什么需要一个统一收口
   （`common/read_limit.go:11-14`）。
2. **`maxBytes+1` 探界，边界不差一**：刚好等于上限的响应能**完整通过**，
   只有真正超出才报错（`common/read_limit.go:43-44`）。这类 off-by-one 是限流/限额
   代码最常见的错，注释把算法讲透了。
3. **非法参数 fail-closed 而不是退化成无界**：`maxBytes <= 0` 返回错误，
   注释直接说明理由 ——「静默退化成无界读取正是本次要修的问题」
   （`common/read_limit.go:46-54`）。
4. **错误可判别**：`ErrReadAllLimitExceeded` 是导出变量，调用方可用 `errors.Is`
   分支处理，而不是靠字符串匹配（`common/read_limit.go:38-39`）。

## 7. 有界写入，且绝不静默截断 —— `model/site_visitor.go:105-129`

```go
	// **必须分批循环写完，不能截断。** 调用方（tracker 的 flush）在取出待写行后
	// 会立刻清空自己的缓冲区，所以这里截断 = 那些行**永久丢失**（不是"下次再写"）。
	// 30 秒窗口内出现超过 siteVisitorMaxBatch 个新 IP 就会触发（例如换源 IP 洪泛）。
	return DB.Transaction(func(tx *gorm.DB) error {
		for start := 0; start < len(rows); start += siteVisitorMaxBatch {
			end := min(start+siteVisitorMaxBatch, len(rows))
			...
		}
		return nil
	})
```

**为什么这是好例子**

1. **它区分了「截断」和「延后」两种处置**：截断在这里等于**永久丢失**，
   因为调用方取出后立刻清空了自己的缓冲区。注释把这条因果链写清楚，
   任何想改成 `rows = rows[:max]` 的人都会先看到警告
   （`model/site_visitor.go:110-112`）。
2. **分批在同一个事务内**：既限制了单次事务持锁时间，又保证全批次原子
   （`model/site_visitor.go:113,166-168`）。
3. **相邻的 `dedupeSiteVisitorRows` 同样是「为了跨方言一致」而必须做**：
   注释解释了 SQLite 与 MySQL 对「同一 INSERT 内两行冲突于同一唯一键」的行为不同，
   先合并才能有确定行为（`model/site_visitor.go:131-136`）。**把方言差异挡在业务层之外。**

> 这条同时是本项目**「审计抓出自己的缺陷」**的实例：独立 Critic 发现「单次 flush
> 超过 500 行会静默永久丢弃访客」（P1-1），修法就是上面的分批循环
> （`计划书/audit/critic-v1.3.129-132.md` P1-1 条）。

## 8. 配置驱动的开关默认值安全（fail-safe 回退）—— `setting/system_setting/task_artifact_store.go:52-75`

```go
// LoadTaskArtifactStoreConfig reads and validates startup-only configuration.
// S3 mode is deliberately disabled until a storage implementation is shipped.
func LoadTaskArtifactStoreConfig() TaskArtifactStoreConfig {
	config := TaskArtifactStoreConfig{ Mode: common.GetEnvOrDefaultString(TaskArtifactStoreModeEnv, TaskArtifactStoreModeUpstream), ... }
	if err := ValidateTaskArtifactStoreConfig(config); err != nil {
		common.SysError("invalid task artifact store configuration: " + err.Error() + "; using upstream mode")
		config.Mode = TaskArtifactStoreModeUpstream
		return config
	}
	if config.Mode == TaskArtifactStoreModeS3 {
		common.SysError("task artifact S3 storage is not implemented; using upstream mode")
		config.Mode = TaskArtifactStoreModeUpstream
	}
	return config
}
```

**为什么这是好例子**

1. **默认值 = 「零行为变化」的那一个**：默认 `upstream` 就是既有的上游代理行为
   （`setting/system_setting/task_artifact_store.go:16,40`）。**新能力默认不改变现状**，
   这是本项目所有灰度开关的统一纪律。
2. **两重保护，都 fail-safe**：
   - 配置**非法** → 回退 upstream 并 `SysError`（不 panic、不静默采纳坏配置）；
   - 配置**合法但后端未实现**（S3）→ 也回退 upstream 并 `SysError`
     （`setting/system_setting/task_artifact_store.go:70-73`）。
   **「用户配了但做不到」必须显式说出来，不能默默当没配。**
3. **校验只做语法层，边界写清**：注释明确「从不解析主机、不联系端点、不验证凭据」
   （`setting/system_setting/task_artifact_store.go:77-78`）——
   避免启动时因外部依赖不可达而卡住，也避免让用户以为凭据已验证。

## 9. 配置驱动的开关默认值安全（保守默认 = 全不生效）—— `setting/response_cache_setting/response_cache_setting.go:19-22`

```go
// 安全默认值（保守起步，指南 §5.2.1）：
//   - `AllowModels` 为空 = **全不缓存** —— 必须由管理员显式加白名单；
//   - `AllowCrossUser` 默认 false = **按 user 隔离**（跨用户泄漏是这项最严重的风险）；
//   - `ChargeOnHit` 默认 true = **照常计费**（不改变既有商业口径，成本节省体现在运营侧）。
```

**为什么这是好例子**

1. **每个默认值的「方向」都是经过取舍的**，而且注释把取舍写出来了：
   - 白名单为空 → **什么都不缓存**（而不是「什么都缓存」）。新特性的默认必须是
     **最小生效面**；
   - `AllowCrossUser=false` → 宁可命中率低，也不冒跨用户泄漏风险；
   - `ChargeOnHit=true` → 缓存省的是**运营成本**，不擅自改变向用户收费的口径。
2. **它把「最严重的风险」直接写在字段旁边**（`AllowCrossUser`），
   所以后续改这个字段的人必然看到它（`setting/response_cache_setting/response_cache_setting.go:56-57`）。
3. **上界有顶**：`MaxTTLSeconds = 86400` 与 `MaxMaxEntries = 20000`
   防管理员配出「永久缓存」/「无界缓存」
   （`setting/response_cache_setting/response_cache_setting.go:28-29`）。

## 10. 前端三态处理 —— `web/src/features/home/components/traffic-stats.tsx:29-51`

```tsx
 * ## 三态
 *
 * loading → 骨架；API 失败 → **整块隐藏**（return null）。理由与既有 `SiteStats` 一致：
 * 访客数是营销信息而非用户数据，读不到时静默隐藏比在落地页弹错误更合适。
 * 但「隐藏」只针对**整块**，不影响页面上任何功能性内容。
 */
export function TrafficStats() {
  const { data, isLoading, isError } = useQuery({ ... })
  if (isLoading) {
    return <TrafficStatsSkeleton />
  }
  // `isError` 与「响应结构不完整」走同一出口：都不显示，避免半截数字误导访客。
  if (isError || !data || !data.visitors) {
    return null
  }
  return <TrafficStatsBody data={data} label={...} />
}
```

**为什么这是好例子**

1. **三态都有明确出口**：loading → 骨架（不是留空导致布局跳动）；
   成功 → 正文；失败 → 整块 `null`。**没有第四种「半渲染」状态。**
2. **`isError` 与「响应结构不完整」合并到同一出口**（`!data || !data.visitors`）——
   注释说明理由是「避免半截数字误导访客」。**这一条正是本项目反复吃过的亏**：
   「接口 200 但字段缺失」会被误当成正常数据渲染出错误的数字。
3. **降级的范围被刻意限定**：只隐藏**整块**，不影响页面上任何功能性内容
   （`web/src/features/home/components/traffic-stats.tsx:31-33`）。**降级不能顺手把功能也降掉。**
4. **它有真实上游约束支撑**：`staleTime: 60_000` 与后端 SWR 的 TTL 一致
   （`web/src/features/home/components/traffic-stats.tsx:39-42`，后端见 ADR-009）。

## 11. 错误处理不吞错 —— `controller/task.go:331-347`

```go
	artifactStore := service.GetTaskArtifactStore()
	if ref, resolveErr := artifactStore.Resolve(task, artifactKey); resolveErr == nil && ref != nil {
		// 本地存储可能在 `Resolve` 与 `Serve` 之间被清理 loop 删掉文件 ...
		// 关键：这里**不能**把错误丢掉直接 return —— 那会让客户端拿到
		// 「200 + 空响应体」，而且**不会**回退到下面的上游代理分支 ...
		if serveErr := artifactStore.Serve(c, task, ref); serveErr == nil {
			return
		} else if !errors.Is(serveErr, os.ErrNotExist) && !errors.Is(serveErr, service.ErrTaskArtifactStoreDisabled) {
			// 非「文件缺失/存储不可用」的错误（如路径非法）应当如实上报，
			// 不要静默落到上游代理去拿一份语义不同的内容。
			writeTaskArtifactError(c, http.StatusInternalServerError, "artifact_serve_failed", "...")
			return
		}
	}
```

**为什么这是好例子**

1. **它把「已知可回退的错误」与「必须上报的错误」分开**：
   `os.ErrNotExist` / `ErrTaskArtifactStoreDisabled` → 继续往下回退；
   其它（如路径非法）→ **明确 500**。注释给出了后者的理由：
   「不要静默落到上游代理去拿一份语义不同的内容」
   （`controller/task.go:343-347`）。**吞错的两种坏法都避开了：既不假装成功，也不乱降级。**
2. **`errors.Is` 而不是字符串比较或 `err == err`**：可判别、可包装。
3. **它记录了被替换掉的坏写法**：注释引用了原实现 `_ = artifactStore.Serve(c, task, ref); return`
   （`controller/task_generic_test.go:603-611`）。**在修复处保留「曾经怎么错」**，
   是防止回退的廉价手段。
4. **有对应的反向锁测试**（见 §2），所以这条修复不会在后续重构里被悄悄改回去。

## 12. 注释解释「为什么」而不是「是什么」—— `common/json.go:12-17`

```go
// hostJSONCodec is the single place where the host chooses its JSON engine.
// Swap the implementation here (for example to sonic.ConfigStd) and every
// common.* and kitutil.* JSON helper, including relaykit DTO (un)marshalling,
// follows. Injected from init() rather than main() so tests run on the same
// engine as production: common is imported by virtually every root package
// and test binary, while main() never executes under `go test`.
```

**为什么这是好例子**

1. **它回答的是「为什么在这里」，而不是「这里做了什么」。**
   读者一眼能看懂代码做了 marshalling —— 注释回答的是**真正难的问题**：
   为什么这是一个单一位置、为什么必须在 `init()` 而不是 `main()` 注入。
2. **「为什么是 `init()`」这条尤其珍贵**：它是一条**反直觉**的约束
   （Go 里通常在 `main()` 做初始化），注释给出了具体原因
   （`common` 被几乎所有包 import，而 `main()` 在 `go test` 下不执行）。
   没有这条注释，后人极可能「顺手」把注入挪到 `main()`，从而**只在测试环境换掉引擎**。
3. **它同时给出了扩展点**：想换成 sonic 只需改这里。**注释指向未来可能的改动**。

## 13. 注释解释「为什么」—— `common/quota_math.go:10-12`

```go
// Quota conversions are centralized here so every billing path shares one
// saturation + logging policy. Single-request charges stay bounded to int32;
// top-ups and wallet-priced purchases use a JavaScript-safe 64-bit domain.
```

**为什么这是好例子**

1. **三句话讲清了一个非常不显然的设计**：
   ① 为什么要集中（共享同一套饱和 + 日志策略）；
   ② 为什么单请求用 int32（批量累加不会逼近 64 位回绕）；

2. **它是「为什么不用裸类型转换」这一全局禁令的落点**：`AGENTS.md:127` 的禁令

3. **解释了「为什么撞上边界就是 bug」**：`saturateQuota` 的注释说明正常运营下单请求
   不会接近这些边界，因此每次 clamp 都记日志
   （`common/quota_math.go:74-81`）。**让「日志噪音」变成「真实异常信号」。**

## 14. 注释解释「为什么」—— `service/site_visitor_tracker.go:70-77`

```go
// visitorDelta 是**待落库的增量**（pending 用）。
//
// 关键设计：pending 存的是**自上次 flush 以来新增的 hits**，而不是累计值。
// 数据库侧写入用的是 `hits = hits + excluded.hits`，所以只有传增量才不会重复累加：
//   - 传累计值 → 第 N 次 flush 会把前 N-1 次的数量再累加一遍（计数虚高）；
//   - 传增量   → 每次 flush 只补上"上次没说过的部分"，总和恰好正确。
```

**为什么这是好例子**

1. **它解释的是一个「看起来两种写法都对」的选择**：pending 里存累计值还是增量，
   代码上都很自然 —— **只有结合 SQL 侧 `hits = hits + excluded.hits` 才能判断哪个对**。
   注释把这个跨层推理写下来了，还**把错误写法会导致的具体后果也写出来**
   （「第 N 次 flush 会把前 N-1 次再累加一遍」）。
2. **这是一条真实的自我纠错**：这个坑是在实测中抓出来的
   （`计划书/workflow_status.md:590-592` 记录「flush 后回访丢计数」与随后的修法）。
   **把踩过的坑写在出事的那行旁边**，是最便宜的知识固化。
3. **注释与代码紧邻**：它就写在 `visitorDelta` 的定义上，
   任何想改这个结构的人必然读到。

## 15. 反面清单：本项目明确不认可的写法

以下都是**真实出过事故或被审计判为缺陷**的形态，遇到就拦：

| 不认可 | 为什么 | 参见 |
|---|---|---|
| `_ = f(); return` —— 丢弃错误后直接返回 | 客户端拿到 200 + 空体，且不走上正确的降级分支 | §11、`计划书/workflow_status.md:279-283` |
| 断言「某标签存在」而不是「标签仍合法」 | 会把「标签被写坏」这类缺陷放行到线上 | §1 |
| 共享可变包级 bool（管理端写 + 热路径读） | Go 内存模型下的无同步并发读写，属未定义行为 | ADR-008 |
| 裸 `io.ReadAll` 读不信任的上游响应 | 一次异常响应就能吃穿单进程内存 | §6 |
| 截断写入（`rows = rows[:max]`）当作「下次再写」 | 调用方可能已清空缓冲区 → 数据永久丢失 | §7 |
| 只为提高覆盖率数字、无断言的测试 | 库全绿但生产零调用/已坏的典型来源 | `AGENTS.md:137` |
| 用「字段在别处的用法」推断「用户会看到什么」 | 同一字段在不同组件里可能承载不同语义 | `计划书/workflow_status.md:676-680` |
| 单一 `refreshing` 标志就宣称「单飞」 | 冷启动并发仍会各算一遍；必须等待在飞计算 | ADR-009 |
| 服务端注入页面上不存在的内容（含未证实数字） | 注入块用户看不到 → 构成 cloaking | ADR-010 |
