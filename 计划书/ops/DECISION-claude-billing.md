# 决策记录：Claude 计费两处疑点（T-C1）

> 决策人：主控（业主已授权自主决策）｜日期：2026-10-21｜状态：**决定暂不改表达式**

## 背景

`计划书/audit-ledger.md` 记录两处未修且未决策的疑点：

1. `hasBillableUsage` 是否应把 **cache tokens** 计入「有可计费用量」；
2. 5m / 1h cache 的写价是否应**分别计价**（当前总量全按 5m 计）。

现有 7 个复现用例固化了「当前行为」，即：现在不是静默错误，而是**已知的语义选择**。

## 决策：不直接改生产计费表达式

理由（按优先级）：

1. **红线优先级最高**：项目记忆 `never-change-production-billing-directly` 记录过一次真实事故（225 次请求多扣费、补偿 $20.86）。计费表达式一旦改错，影响所有真实扣费，且不可追回。
2. **当前行为有测试锁定**：7 个用例描述的就是现状；直接改会同时改掉「契约」，没有灰度手段。
3. **影响面未量化**：改之前必须知道「有多少请求带 cache token、差异金额多大」，这需要生产 SQL 统计，而统计口径本身依赖第 1、2 条的语义选择（鸡生蛋）。
4. **没有回滚粒度**：表达式是全局的，回滚=再发一版；不像前端可以灰度。

## 允许的推进路径（按顺序，均不需要业主再拍板）

| 步骤 | 内容 | 风险 |
|---|---|---|
| 1 | 用生产 SQL 统计：近 30 天带 `cache_read_input_tokens` / `cache_creation_input_tokens` 的请求数与金额占比 | 只读 |
| 2 | 在**非生产分组 + 独立 token** 下用影子模式同时算新旧两套价，落日志对比 N 天 | 不改生产表达式 |
| 3 | 差异分布已知后，若差异 < 0.5% 且方向一致，提交变更 + 双跑对照 + 灰度分组 | 需灰度开关 |
| 4 | 若差异大或方向不一致，维持现状并把语义写进 `计划书/ops/ADR-架构决策记录.md` | 零风险 |

**停止条件**：第 1 步的统计必须由业主指定的时间窗口执行；未得到窗口前停在本文档。

## 当前结论

**不改代码。** 两处疑点保持现状（有测试锁定），推进路径与判据已写明。
任何「顺手改一下计费」的提议都应被本记录拒绝，直到第 2 步数据出来。
