1. 为什么要做

起点是一个功能需求：让用户在明确授权后，把自己与模型的对话匿名采集到云盘，用于训练数据积累；管理员可随时关闭，用户可随时撤回，撤回即不再采集。

但真正的问题不在功能本身，而在它被加到哪里——一个正在线上跑的 API 网关，请求路径上每一微秒都直接换算成用户体验。所以我给自己定的第一约束不是「功能能跑」，而是：

  • 绝不拖慢用户请求（采集必须完全脱离请求路径）
  • 绝不丢数据（采集不可逆——上传过就不再回看，丢了就是永久丢）
  • 绝不骗人（做不到的边界要写在界面上和代码里，不能用「看起来能用」顶上）

2. 直觉：三个反直觉的判断

判断一：注释里写「绝不会」的时候，必须有并发用例去证伪它

我最初写的三处代码，注释都在宣称一个没被验证的保证。独立审查把它们全抓了出来：

缺陷我的注释当时怎么说真相
BLOCKING 队列投递 「关闭后一律返回 false，不 panic」 会 panic。且发生在 relay goroutine 上时杀掉整个网关进程。条件只是「停机与在途请求并发」——正常运维。
BLOCKING 撤回授权 「撤回时主动失效缓存，使撤回立即生效」 只在无并发时成立。并发下旧的「已授权」会写回缓存，用户继续被采集最长 30 秒——这是隐私事故。
BLOCKING 增量判定 「历史被改动 → 保守全量重传」 只对末位成立。历史中间被编辑时校验通过 → 被改内容永久不再上传。

共同点：原实现的测试恰好都是串行的，全部绕过并发窗口。所以「我测过了」在有并发的地方几乎不构成证据。

修 B1 时我先试了「用锁让检查+发送与close互斥」——修好了，但热路径从 2.4µs 涨到 11.6µs（5 倍）。改成根本不关数据通道（另开 stop 通道表达「停止消费」）后：安全与性能同时成立，热路径 1.93µs，比原实现还快。
教训：遇到「加锁才安全」，先问能否从设计上消除共享，而不是直接上锁。

判断二：「自适应」如果读的是宿主机内存，在容器里就是 OOM

你指出 900MB 预算锁死不合理，应该按机器内存自适应取 80%。直觉上直接读系统内存就行——但那是个会杀进程的坑：

容器里 mem.VirtualMemory() 返回的是 宿主机 内存。
限 512MB 的容器跑在 64G 宿主机上，
按宿主机 80% 预算 = 采集自己吃掉 50GB
→ 被 OOM killer 杀掉，表现为「容器无征兆重启」，极难排查。

所以检测顺序是 cgroup v2 → cgroup v1 → 宿主机 → 安全下限，并且取 min（容器可能同时受两者约束）。

判断三：64KB 截断不是「限制」，是「丢数据」——你也是对的

你原话是「遇到二三十 MB 的可以压缩完再上传」。我原来做的是砍掉，不是压缩。对训练数据来说，一个 30MB 的代码对话只存 64KB，是残缺样本，比不采更糟。

改成 gzip 压缩后上传（BestSpeed）。实测压缩率对对话类 JSON 约 1/5 ~ 1/10，让单分片能装 20~40MB 原文，同时上行带宽占用降一个量级——而上行是全站共享的，省带宽就是直接保护用户请求延迟。

顺带修掉一个我自己写的、很难发现的 bug：截断函数返回的是text[:cut]子串，Go 的子串共享底层数组——于是「截断到 64KB」的每条信号背后，仍钉着完整的 10MB 原文。1024 条队列最坏钉住 10GB，所谓「内存硬闸门」根本不存在。修法：strings.Clone，并写了用 unsafe 指针比对来证明不再共享的回归测试。

3. 做了什么

3.1 功能：训练数据采集（Spec-008）

能力实现要点
用户授权 + 免责声明 开启必须经免责声明弹窗勾选确认；撤回立即生效（无 30s 窗口）；撤回只停止后续采集、不删除已上传数据——这条边界写在界面小字里，不写模糊承诺。
管理员总开关 默认开，但前提是云盘已配置；关闭后用户侧不渲染开关（不给「点了没作用」的按钮）。
目录结构 日期/用户名-用户ID/模型/part-NNNN.jsonl.gz。用户名是用户可控输入 → 白名单净化 + 强制追加用户 ID 消歧（防路径穿越与跨用户覆盖）。
增量识别 按文本前缀做增量：只在「新文本以旧前缀开头且前缀哈希一致」时裁剪（此时 new = old + suffix 是恒等式，不可能丢内容）。用户消息里重复的段落不会被误判为新轮次。
异步 / 不拖慢请求 热路径只做三件事：读一个原子布尔量 → 从调用方已算好的 meta 取文本 → 一次非阻塞入队。全部在 gopool.Go 内，响应体已返回。
自适应内存 cgroup 感知的 80% 预算，派生单条上限 / 分片上限 / 队列容量；全部可用环境变量覆盖；启动日志打印预算与来源。
压缩 分片 gzip 后上传（.jsonl.gz，后缀即契约）；读取侧带 zip-bomb 防护。
管理端 总览（今日统计 / 云盘配额 / 队列 / 在传字节实时值）、云盘文件下钻浏览 + 预览 + 删除、对话深度分析 + 继续追问（复用 relay 栈，费用记管理员账）。

3.2 补漏：接线时发现的三个真实缺陷

#缺陷为什么致命
1增量完全失效 网关只能拿到一整块拼接文本，每次请求只有 1 条消息；而水位按消息条数算 → 恒为 1 → 每次都全量重传。正是你点名要避免的。新增按文本前缀做增量。
2StopWorker 停不掉 worker 阻塞在队列的 stop，而 StopWorker 关的是 workerStop——两个不同的 channel。停机/关闭采集后 worker 永久挂住。
3限速器读全局变量 前一用例关掉 workerStop 后，后续用例的限速等待立即返回（该等 0.5s 却等 0s）。改为实例字段注入。

还修了日志轮转的一个静默失效：按大小轮转时两次可能落在同一秒，文件名相同 → O_APPEND 继续写原文件，「轮转」失效且日志里看不出异常。我最初写的兜底「改用纳秒时间戳就必然唯一」是错的——被我自己写的 261 次连环轮转用例抓出来。
