1. 为什么要做

起点是一个功能需求：让用户在明确授权后，把自己与模型的对话采集到云盘，用于训练数据积累。管理员可随时关闭，用户可随时撤回，撤回即不再采集。

但真正的问题不在功能本身，而在它被加到哪里——一个正在线上跑的 API 网关，请求路径上每一微秒都直接换算成用户体验。所以第一约束不是「功能能跑」，而是：

  • 绝不拖慢用户请求（采集完全脱离请求路径）
  • 绝不丢数据（采集不可逆——上传过就不再回看）
  • 绝不骗人（做不到的边界要写在界面上和代码里）

这个约束在后面被反复验证：它既是设计的来源，也是几乎每一个严重缺陷的判定标准。

2. 直觉：五个反直觉的判断

判断一：注释里写「绝不会」时，必须有并发用例去证伪它

最初三处代码的注释都在宣称一个没被验证的保证。独立审查把它们全抓了出来：

缺陷我的注释当时怎么说真相
BLOCKING 队列投递 「关闭后一律返回 false，不 panic」 会 panic，且发生在 relay goroutine 上时杀掉整个网关进程。触发条件只是「停机与在途请求并发」——正常运维。
BLOCKING 撤回授权 「撤回时主动失效缓存，使撤回立即生效」 只在无并发时成立。并发下旧的「已授权」会写回缓存，用户继续被采集最长 30 秒——隐私事故。
BLOCKING 增量判定 「历史被改动 → 保守全量重传」 只对末位成立。历史中间被编辑时校验通过 → 被改内容永久不再上传。

共同点：原实现的测试恰好都是串行的，全部绕过并发窗口。

修「队列 panic」时我先试了「用锁让检查+发送与 close 互斥」——修好了，但热路径从 2.4µs 涨到 11.6µs（5 倍）。改成根本不关数据通道（另开 stop 通道表达「停止消费」）后：安全与性能同时成立，热路径 1.93µs，比原实现还快。
教训：遇到「加锁才安全」，先问能否从设计上消除共享。

判断二：「库全绿」和「生产可用」之间，隔着一次真实调用

独立审查给出 FAIL，理由是发现了一个 P0：

管理端所有接口全部 404。

后端把新路由注册在了 api-router.go 的 adminRoute 里——而它的父组是 /user，所以实际前缀是 /api/user/...。
前端调的是 /api/admin/...。整套管理界面（训练数据 + 运营面板）全挂。

为什么测试没抓到？因为当时的测试全是「直接调用 handler 函数 + 拼一个字符串 URL」——handler 根本不校验路径，URL 只是个装饰。库全绿，生产全挂。

修法不只是改路径，而是补上会拦住它的那一层：

  • 按项目既有范式（web-protection）新建独立 router 文件，统一挂 /api/admin/...
  • 新增路由契约测试：① 断言声明的每条路由真的注册进 gin；② 扫描前端源码里每个 /api/... 调用，断言它都能在后端路由表里找到；③ 一条反回归断言：不得出现 /api/user/training-data

RED 验证：临时把一个前端路径改错 → 测试立即失败，并打印「该功能会在运行时 404」。

这与本项目记忆里反复出现的「模块库全绿但生产零调用」是同一类缺口。测了函数不等于测了链路。

判断三：压缩是省带宽，但「先压缩再切片」是把数据切坏

你指出「二三十 MB 的可以压缩完再上传」。我做了 gzip。但第一版是错的：

payload → gzip 成一个 member → 把这个 member 的字节按 4MB 切开 → 写成 part-1/2/3

结果：每个 part 都是 gzip 的【碎片】
  chunk[0] decompress → unexpected EOF
  chunk[1] decompress → gzip: invalid header
  chunk[2] decompress → gzip: invalid header

而且不是报错，是静默乱码：预览按 gzip magic 判断失败后当明文显示二进制；分析端把碎片当明文喂给模型。

正确顺序：先按行切原始 JSONL，再对每块各自 gzip——每片都是完整的 member，可独立解压。

顺带建立一条不变量：分片原始上限 ≥ 单条文本上限 × 8（JSON 最坏转义约 6 倍）。没有它，一条超长记录会被 splitBySize 的硬切兜底切成两半 → JSONL 数据集永久不可解析。

RED 验证：临时改回旧顺序 → 测试失败并打印出泄漏的 gzip 魔数 \x1f\x8b。

判断四：登录名不是身份证明

上游 2026-09 修了一个 GitHub 绑定迁移的问题，我们没跟。核对后发现我们确实有同样的漏洞，而且更严重：

历史绑定迁移的逻辑是：「GitHub 登录名 == 我库里存的旧值」→ 迁移 → 直接登录该账号。

而 GitHub 允许改名，释放出来的旧登录名任何人都能抢注。抢到之后用 GitHub 登录本服务，就被当成那个历史账号的主人 → 账号接管。

修法（fail-closed）：迁移必须有一条已验证邮箱与目标账号邮箱一致的证据；拿不到已验证邮箱、或邮箱不匹配 → 拒绝迁移并写安全审计。
拒绝迁移不等于拒绝登录——用户仍可用其它方式登录后再显式绑定。宁可让少数老用户手工重绑，也不冒账号被接管的风险。

顺带排除纯数字的 legacy 值（不可能是登录名，防「数字 id 恰好等于某人登录名」的碰撞）。新增 5 条用例，含「攻击者邮箱」与「类型不对的 Extra」场景。

判断五：截断保留头部，等于让尾部永远采集不到

文本超限时我原本只保留头部。但对话是增长的——新内容在尾部。

会话变长 → 头 N 字节【不变】→ 前缀指纹校验通过 → 增量后缀为空
         → 尾部新内容【永远不被采集】

这正是「长期会话要能识别增量」这一核心需求的反面。

修法：截断保留头 + 尾（含省略标记，总长仍严格 ≤ 上限）；信号带 TailOnly，worker 对超限会话按尾部做增量——对整段做前缀比对会因省略标记的长度变化而每次全量重传。

一个自省：这条是我在「用户说 64KB 太小」之后改的。第一版只做了压缩、没意识到截断方向本身就是错的。改一处要顺着链路看完，而不是只改被点到的那一处。

3.2 接线时发现的三个真实缺陷

#缺陷为什么致命
1增量完全失效 网关只能拿到一整块拼接文本，每次请求只有 1 条消息；而水位按消息条数算 → 恒为 1 → 每次都全量重传。正是你点名要避免的。
2StopWorker 停不掉 worker 阻塞在队列的 stop，而 StopWorker 关的是 workerStop——两个不同的 channel。停机后 worker 永久挂住。
3限速器读全局变量 前一用例关掉 workerStop 后，后续用例的限速等待立即返回（该等 0.5s 却等 0s）。

还修了日志轮转的一个静默失效：按大小轮转时两次可能落在同一秒 → 文件名相同 → O_APPEND 继续写原文件，轮转失效且日志里看不出异常。我最初写的兜底「改用纳秒就必然唯一」是错的——被我自己写的 261 次连环轮转用例抓出来。
