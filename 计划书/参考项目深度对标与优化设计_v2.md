## 4. 差距分析（主项目现状 → 参考高价值点）
1. **可观测性差距**：我们有 consume log（frt/explain/stream_status）+ 渠道健康分，但**无 OTel/标准化 trace 导出**；参考 hermes-otel/agenttrail 提供实时事件流。→ 建议补 OTel 导出（低侵入：在已有埋点处加 span）。
2. **小白易用差距**：已有 onboarding 计划（B2-3）未落地；参考 addyosmani agent-skills 的"质量门即教程"、agenttrail 的"边用边看"——把日志转成用户可理解的时间线（B2-2 请求 trace）。
3. **Skills 沉淀差距**：参考多个 skills 框架（工程化/渐进式）；我们 B3-3 需把"技能=流程+验证+示例"标准化。
4. **回退路由**：9router-Max 智能回退→我们 stream_fallover 默认关；建议按 B1-1 灰度→默认开（需先解决上游稳定渠道）。
5. **号池/账号管理 UX**：chatgpt2api 多账号导入→我们 MultiKey 可借鉴导入/健康/轮换可视化。
6. **品类扩展**：电商/视频/图片参考项目均 OpenAI 兼容→我们网关天然可服务；需在任务插件体系加品类模板（B4-3 试点）。

## 5. 优化设计（分 4 波，全部映射主项目现有路径，跨栈适配）
### 波 1（P0 可观测 + 回退，安全可回滚）
- OTel 导出（go.opentelemetry.io 或轻量自研 span 埋点）：在 `service/billing_session`、`model/channel_cache`（选渠道）、`relay/channel/api_request`（上游/首包）处补 4-5 个 span；前端不动；开关 env 默认关。
- stream_fallover 灰度开启调研（B1-1）：先补"空流判空对齐 free-router 细节"（只 reasoning 无 content/tool_call 视为失败），开关默认仍 off，观察后开。
### 波 2（小白易用 + 日志透明化）
- 落地 B2-2 请求时间线（复用 consume log other + 渠道选择/冷却记录，零额外计算）+ JSON 导出。
- 落地 B2-3 onboarding 3 步 + 错误码人话扩展（渠道冷却/额度不足/上游限流/IP 封禁）。
### 波 3（Skills + 记忆，轻量）
- B3-3 Skill 包标准化（SKILL.md + 质量门 + 示例；复用 CI 校验）。
- B3-2 记忆层 v1（规则+衰减，Redis TTL；不引向量库）。
### 波 4（品类扩展试点）
- B4-3 试点 1 个（优先电商详情页生成或图片生成）：在任务/工具插件体系接入 OpenAI 兼容能力，白名单灰度。
