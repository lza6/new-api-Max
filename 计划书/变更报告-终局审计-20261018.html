1. 为什么要做这一轮

系统已经在生产跑。此前几轮修的都是「看得见会报错」的问题。但生产环境里更危险的是另一类：

  • 按钮在、接口在、测试全绿，用户点下去却永远失败；
  • 页面显示一个自信但错误的数字，而且没有任何标志提示它可能不对；
  • 文案承诺了一件事，代码做的是另一件事。

这类问题不会报错、不会告警，只会让运营者基于错误信息做决策。因此这一轮的做法是： 先派只读审计代理沿链路找「声明与实现不一致」，再由主线程逐条复现、修复、验证。

2. 关键直觉：三种「假完成」

① 契约假完成：单测只测错误路径

分析接口的测试覆盖了「缺 path」「空内容」「只传 system」等错误分支 —— 这些都对。但成功路径从没被测过（因为不能真花钱调模型）。 于是「成功时前端必然抛错」这个 P1 缺陷，在测试里完全隐形。

教训：只测错误路径的测试，会让「功能整体不可用」看起来像「功能正常」。

② 深度假完成：断言太弱，等于没断言

云盘计数在真机测试里断言了 folders >= 1，从不断言 files。 而缺陷恰恰是 files 恒为 0。测试通过了，错误却活着。

教训：断言必须覆盖「这个功能存在的理由」，而不是只覆盖「它没崩」。

③ 口径假完成：数字对了，但读法错了

「剩余额度」排除了管理员，「消耗排行榜」却没排除。两个数字并排显示， 运营者会看到「榜首消耗最多，但他的额度不计入剩余额度」这种自相矛盾的画面， 然后怀疑哪个数字没刷新 —— 实际上两个都是"对"的，只是口径不同。

教训：同一屏上的数字必须共用口径，否则它们互相拆台。

3. P1：分析功能全链路不可用

P0/P1 深度分析、分析报告、继续追问 —— 三条需求在生产中全都不可用。

现象与根因

后端把 /analyze 交给 relay 栈处理。relay 成功时写出的是上游的原始 chat completion：

{ "id":"chatcmpl-x", "choices":[ {"message":{"content":"..."}} ] }   // 没有 success 字段

而参数错误走 common.ApiErrorMsg，写出的是本项目信封：

{ "success": false, "message": "..." }

两者都是 HTTP 200。前端却按信封解包并判断：

if (!res.success) { throw new Error(...) }   // 成功时 res.success 是 undefined
                                             // !undefined === true → 必然抛错

为什么一直没被发现

既有测试只覆盖错误路径（付费红线不允许真实调用模型）。 所以「成功路径必崩」从来没有被执行过。

怎么证明这不是我猜的

Playground 走的是同一条 relay，它一直直接读 choices、不判 success。 同一后端、两种前端写法，Playground 能用而分析不能用 —— 反证原判据是错的。

修法

  • api.ts 原样透传原始响应，不再按 {success,data} 解包；
  • 判据改为 success === false（绝不能写 !success）， 并额外兜住 relay 自身的 {error:{message}}；
  • 类型如实建模三种形态，并在注释里写清「为什么不能写 !success」。

RED 验证：把信封解包改回去 → 新增的 3 个契约测试立刻 2 个失败。

4. 文件数恒为 0（自信但错误的数字）

HIGH 管理员看到「N 个文件夹 / 0 个文件」，且 truncated=false。

根因：遍历深度差了一层

采集布局是 日期 / 用户-ID / 模型 / part-*.jsonl.gz，即分片在第 4 层。 而调用写死 CountItems(ctx, 3)：

列 root(0) → 日期(1)      ✅ 入队
列 日期(1) → 用户(2)      ✅ 入队
列 用户(2) → 模型(3)      ❌ 2+1 < 3 为假 → 不展开
                            → 模型目录只被"计数"，内部文件一个也数不到

后果不是报错，而是一个看起来完全可信的 0。管理员会以为采集根本没写数据。

修法

  • 新增 CaptureLayoutDepth = 3 常量（与布局同源），调用处传 +1；
  • 把遍历抽成纯函数 countTree，让深度语义可以离线穷举 （真机复现需要真实 OneDrive 层级）；
  • 补上真机测试里缺失的 files > 0 断言。

新增 6 个用例，其中一个正面锁定缺陷本身： 用布局层数作深度时，断言 files==0 且 truncated==false。

5. 分析正文丢了「谁在说话」

P1 模型会把自己生成的回复当成「用户原话」引用进分析报告。

来龙去脉

上一批上线了「模型回复也采集」，记录里现在有两类行： role:"request"（用户侧）与 role:"assistant"（模型回复）。 但组装分析正文时只写了 rec.Content，把 role 丢掉了。

而分析提示词明确要求「逐字引用用户原话」。正文里两类文本混在一起、没有任何标注， 模型无法区分 —— 于是它摘录的「用户原话」可能整段都是它自己说过的话。 报告从根上不可信，而且管理员完全看不出来。

修法：一次扫描产出两个视图

Text
忠实拼接原文，不加任何标签（数据保真视图，将来用户导出自己的数据不该夹带中文标注）
AnnotatedText
逐行带角色标注，专供分析提示词

标注来自记录里现成的 role 字段 —— 是数据结构事实，不是猜测。 这与 SplitHeuristicTurns 那种「从拼接文本里猜角色」是两码事：那个会误判，这个不会。

提示词同步改写：明确告知标注语义、禁止把【模型回复】当用户原话， 并说明「请求侧那一行是拼接文本，逐轮配对不可靠」。

6. 同意书与真实采集面不符

P1（合规） 免责声明只说「采集你的输入」， 没说模型回复同样入库、管理员可查看并导出原始对话。

这不是措辞问题：模型回复经常复述用户贴过的密钥、报错堆栈、内部地址， 敏感面比「只采输入」大得多。不写清楚，用户的「同意」就不算知情同意。

两个连带动作

  • 新增声明条款（7 语言）；
  • 递增 CurrentPolicyVersion v1 → v2，使旧同意失效、重新征求。

顺手逮住一个「我自己引入的 UX 回归」

版本一升，已授权用户的开关会从「开」悄悄变成「关」，界面不给任何解释。 用户会以为功能坏了、自己误触了，甚至怀疑数据在被偷偷继续采集。

修法：新增 needs_reconsent 下发，界面明示 「采集已暂停，请重新确认新说明」。而且只在声明改版时为 true —— 从未同意 / 主动撤回时不提示（否则是噪音）。

7. Web 防护「没有翻页」的真根因

根因不是后端缺分页。后端三张表全部支持 page/size 且返回 total。 也不是前端没用分页组件 —— 页面确实算了 pageCount。

真正的原因是一条隐藏的依赖链：

DataTable 默认把分页控件 portal 到"页脚容器"
  → 该容器由 SectionPageLayout 的 PageFooterProvider 提供
    → 页面没套 SectionPageLayout
      → 没有 Provider
        → PageFooterPortal 直接 return null
          → 界面上一个页码都看不到

修法：套 SectionPageLayout（顺带补齐页面标题 —— 原先没有标题/面包屑， 正是「不够高级、比较简陋」的观感来源），并把自搓的 Button 切换换成项目既有 Tabs。

排查记录：扫了全部 feature 首页，另有两处未用该布局但不需要 —— pricing 用客户端分页且显式渲染分页组件；system-settings 的表格在对话框内部。故只改真正受影响的两页。

8. 排行榜口径不一致

「剩余额度合计」只统计 role < AdminUser，但消耗排行榜不排除任何人。 管理员常拿自己账号跑分析/测试（分析费用就记在管理员账上），会长期霸榜， 真正的消耗大户被挤下去。

修法：SQL 侧 user_id NOT IN (管理员ID)。之所以不 JOIN users： 日志库可能是另一个库（ClickHouse），跨库 JOIN 不可行。

自查时发现我自己写的回退路径是错的

管理员数量超过内联上限时会退化为 Go 侧过滤。我第一版写的是「按 limit 取行再过滤」—— 管理员占满前 limit 个位置时，过滤后剩 0 行，真正的消耗大户完全不可见。

测试当场抓住了它（[] should have 1 item(s), but has 0）。 改为多取 len(adminIds) 行再过滤，并设 2000 行兜底防巨量扫描。 实测日志：fetched 552 rows, kept 1。

9. 「几月几日采了多少」真正落地

/by-date 此前是孤儿接口（前端从不调用），且只返回当日进程内计数， 历史日期一律 known:false —— 等于这条需求没做。

云盘目录树的一级目录就是日期，是唯一持久且真实的采集记录。 新增 AggregateDailyStats 从目录树聚合：每天的用户数 / 模型数 / 分片数 / 字节。

必须说清的口径（同一屏两个数字本就允许不一致）

来源含义优点局限
今日统计卡（进程内计数）本次进程启动以来的量实时、含未上传量重启归零、只有今天
每日历史卡（云盘聚合）已成功落盘的量可回溯任意日期、重启不丢只反映已上传成功

卡片内写明来源，避免管理员把差异当 bug。

10. 我自己引入的配额风险

这不是优化，是保护。管理端轮询会持续调用云盘 API， 而采集 worker 用的是同一份速率配额 —— 管理端把配额打满， 采集上传就会 429/限流，表现为「采集莫名开始失败」，根因却在另一个页面。

修法：新增 timedCache[T]（TTL + singleflight）：

  • 每日聚合缓存 5 分钟（这张表不需要秒级新鲜，每次刷新代价是一次全量列举）；
  • 目录/文件计数缓存 1 分钟（总览 5s 轮询不再每次遍历目录；队列/在传字节走内存计数，不受影响）；
  • 只缓存聚合结果，不缓存原始目录树：十万条约 10MB，驻留内存与「内存有硬上限」冲突；
  • 错误不进缓存：云盘恢复后应立刻看到数据，不该继续吃 5 分钟旧错误；
  • Redis 未启用时也生效：打满配额的风险不该取决于是否配了 Redis。

RED 验证：完全绕过缓存后，16 并发 → 16 次云盘调用（正是生产风险），测试立刻失败。

14. 独立审查线程的复验（它推翻了我自己的结论）

我请了一个只读审查线程，用六个维度复核本批 9 个提交。它找出了 3 个阻塞 —— 其中两个是我自己引入的，还有一个推翻了我此前的验证声明。

B1（P0）「每日历史」100% 报错：默认路径返回空响应

if date == "" || date == today {
    out["stats"] = stats
    out["known"] = true
    return          // ← 漏了 common.ApiSuccess
}

Gin 什么都不写 → HTTP 200 空 body。而前端「每日历史」卡从不传 date， 所以它 100% 拿到空响应、解析失败、报 "Failed to load"。 只有显式查历史日期才正常 —— 这让排查极易跑偏到前端。 既有测试只覆盖「非法日期」与「历史日期」，恰好绕开这两条默认路径。

为什么值得单独讲：这是「只测错误路径」的又一次复现 —— 上次它藏住了分析功能全链路不可用，这次藏住了每日历史不可用。

B2（P0）worker 启停的数据竞争与僵尸 worker

runWorker 无同步地读包级 workerStop，而 StartWorker 在锁内写它。逻辑后果比竞态报告更严重：

StopWorker 关闭 C1 → StartWorker 立刻把全局换成 C2
  → 尚未调度的旧 goroutine 读到 C2（未关闭）→ 永不退出
    → 两个 worker 同时消费同一队列
      → 同会话水位并发读写，后写覆盖前写 → 增量重复或丢失

修法：stop/done 作为 参数传给 goroutine；StopWorker 等 done 真正关闭； StartWorker 先等旧 worker 退出。

⚠️ 我此前的一条不实声明

上一批提交信息里我写了「-race 同范围 PASS」。 实际上那次用的是窄 -run 过滤，恰好没包含 TestWorkerCanRestartAfterStop； 整包 -race 当时是 FAIL。

教训：验证声明的范围必须与结论的范围一致。 说「全包通过」就必须跑全包；跑了 5 个用例不能说「相关范围通过」。

B3 分析功能的「默认操作路径」仍然是坏的

界面标 Model (optional)，而后端 relay 对空 model 直接 400。 「打开面板 → 不改模型 → 点开始」是管理员的默认路径，却必然失败； 且报错来自 relay 通用校验、与「分析」无关，管理员根本不知道该改什么。

修法：后端在调用模型前给出点名 model 的错误；前端改必填并在空值时禁用按钮。

二轮复验又抓到一个 P0（既有缺陷）：路径语义错位

ListTree(root) 返回的是相对 root 的短路径， 但四个调用方——前端下钻、预览、删除、分析——全都按完整路径使用。

浏览 2026-10-14 → 后端返回 "alice-1"
  → 前端拿它当下一层的 path → 请求 RootPath/alice-1（缺日期前缀）
    → Graph 404 → 被 fetchEntries 当成「空目录」
      → 界面显示「No files yet」   ← 失败伪装成"数据为空"
分析：ReadFile("part-0001.jsonl.gz") → 404 → 全部计入 SkippedParts
      → 报「没有内容」              ← 同样是"空"而不是"错"

修法：统一返回完整路径（root=="" 时行为不变）。前端本来就有 startsWith(prefix) 的显示裁剪，无需改动。

⚠️ 为什么我自己的端到端测试没抓到它

controller 层的 fakeReaderSink 返回的是完整路径， 而真实 OneDrive sink 返回的是相对路径。两者语义相反， 于是「端到端测试」只验证了计数逻辑，和真实后端一起撒谎。

教训：对「路径 / 单位 / 顺序 / 编码」这类契约， 必须用真实实现 + 假传输层来测，不能用「假对象 + 假传输层」—— 后者测的是假对象的行为，不是产品行为。
