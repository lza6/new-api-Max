## 4. 主题详细任务卡

### 4.1 v2.x 高可用与性能（P0/P1）

#### 4.1.1 热路径缓存（✅ 已闭环 v1.3.47 · 真实缺口=订阅档位解析）
- **研究结论（2026-09-28 证据）**："用户设置/定价快照加缓存"的前提**不成立**——审计确认：用户 `GetUserCache`（Redis+AuthVersion 栅栏，user_cache.go）、token `GetTokenByKey`（Redis，token_cache.go）、渠道（channel_cache.go 运行快照）、计费（billing_setting 内存结构）、定价 `GetPricing()`（1min 内存缓存 + InvalidatePricingCache 挂在 channel/option 写路径）**均已有缓存**；relay/middleware 热路径零直接 DB 调用。**勿重复造轮子**。
- **真·缺口**：限流中间件 `middleware/subscription-rate-limit.go:73` `resolveSubscriptionTier` 对「有 active 订阅」用户**每请求一次** `GetAllActiveUserSubscriptions` DB 查询（无订阅用户已有 15s 负缓存 `service.CacheNoSubscription`）。
- **落地（v1.3.47，低风险）**：
  1. `model/subscription_tier_cache.go`：进程内正缓存（key=userId → active 订阅摘要，TTL=env `SUBSCRIPTION_ACTIVE_CACHE_SECONDS` 默认 10s，0=关闭回退基线）。
  2. `middleware/subscription-rate-limit.go`：缓存优先 → 未命中查 DB 并存回 → 摘要算档位（`resolveFromSubscriptionSummaries`，语义与既有 subs[0] 完全一致；套餐本身有缓存）。
  3. 失效（model 内调用，无 model→service 环）：`CreateUserSubscriptionFromPlanTx` / `AdminInvalidateUserSubscription` / `AdminDeleteUserSubscription` / `resetUserSubscriptionTx` / `downgradeUserGroupForSubscriptionTx` / `ExpireDueSubscriptions` 每用户。
  4. **计费不应缓存**：`NewBillingSession` 的 `HasActiveUserSubscription` / `AllowWalletOverflow`、`PreConsumeUserSubscription` 保持 DB 权威（只缓存纯软限的限流档位）。
- **v1.3.48 审计补位**：`AdminSetUserSubscriptionTier`（PATCH 档位覆盖）补缓存失效（覆盖变更即时生效）；缓存容量淘汰由整表 `clear` 改为「先清过期、仍达上限随机删至一半」（严格有界 + 保留热点）；README 登记 `SUBSCRIPTION_ACTIVE_CACHE_SECONDS`。
- **测试**：`model/subscription_tier_cache_test.go` 5 用例（命中/未命中/失效/禁用/过期 1.1s/并发 50 goroutine）。
- **E2E 验收**：rpm=1 套餐授权用户 → 第 1 次中继放行、第 2 次 429「订阅请求速率已达上限」；作废订阅后（TTL 窗口内）不再 429（即时失效）。证据 `计划书/e2e-evidence/v1.3.47-subscription-tier-cache.json`。
- **DB 削减口径**：订阅用户每请求 1 次 DB → 每 TTL(10s) 1 次 + 变更即时失效。
- **回滚**：`SUBSCRIPTION_ACTIVE_CACHE_SECONDS=0`（逐位回退基线）+ commit 回退。

> 后续若需横向规模化：负/正订阅缓存可升级 Redis 共享（当前进程内，与既有 no-subscription 负缓存及进程内 RPM 计数同口径）。

#### 4.1.2 连接池/HTTP 复用收敛（✅ 已闭环 v1.3.49 · 共享调优 Transport）
- **研究结论（2026-09-28）**：webhook/通知已走 SSRF 客户端（复用）；`model_sync/ratio_sync` 自建 SSRF 拨号 transport（低频，不合并）；**真缺口**＝中继渠道适配器 ollama(5)/ali/kilwa 每请求新建 `&http.Client{}`，走 `http.DefaultTransport`（`MaxIdleConnsPerHost=2`，高并发同上游 keep-alive 复用不足）。
- **落地**：`common/outbound.go` 共享调优 Transport（PerHost=32/Total=100，TLS 随 `TLSInsecureSkipVerify`）+ `NewOutboundClient(timeout)`；7 处渠道客户端改包级复用共享池，各自 Timeout 语义不变（30min/1h/120s/不限时）。
- **测试**：`TestOutboundSharedTransport`（指针同一=同池 + 调优下界）。
- **审查 P1-1 修复（v1.3.50）**：共享 Transport 必须**在构建函数内直读 env**（`GetEnvOrDefaultBool`），不可依赖包级 var 顺序或 `sync.Once`——渠道适配器包级 client 初始化早于 `main/InitEnv`；`TLS_INSECURE_SKIP_VERIFY` 当时读 false。已修 + 测试锁定。
- **纪律**：新增外呼点——渠道/网关配置受控 URL 用 `common.NewOutboundClient` 复用共享池；用户可控 URL 走 SSRF 客户端；禁止再裸建 `&http.Client{}`；「启动期依赖 env 的共享对象」一律在构建函数内直读 env。
- **回滚**：渠道客户端逐个改回 `&http.Client{}`（行为等价，仅连接池降级）。

## 5. QA / 工程标准（横切所有主题）

### 5.1 RIPER-5 执行流程（每批强制）
1. **R 研究**：读现状证据 + 相关深挖文档 + 台账；分解需求、定位文件/符号、追踪链路；**严禁此阶段提方案/改码**。
2. **I 创新**：≥3 个方案（传统/优化/创新）+ 多维度评估（可行/成本/维护/性能/扩展/风险/可衍生/UI 可观性）+ 权衡矩阵；**不写实现细节**。
3. **P 规划**：选定方案 → 原子任务（目标文件/函数/变更/验收/风险）+ 执行顺序 + 质量检查点。
4. **E 执行**：严格按序 TDD；每步可测性验证；异常即停、记录、回退到稳定态。
5. **R 回顾**：成果验证（对照原始需求）、变更摘要、环境清理、质量报告、经验沉淀、归档 + 台账更新。
> 说明：执行 AI 在「研究/创新/规划」阶段输出方案供主控/用户确认；「执行」阶段自主推进；每批完成即进入下一批。

### 5.2 测试策略（务实守护关键路径）
- 计费/安全/三库不变量：单测锁定（`quota_math_test`、`openai_image_request_test`、`auth_token_test`、`verification_test`、三库 conformance）。
- 前后端契约：契约测试 + 浏览器 E2E（HTTP + 真实浏览器双证）。
- 覆盖率：关键路径 ≥90%；不为数字写无断言测试；既有失败噪声按台账排除，不误判回归。
- 验收矩阵：每任务卡含「验证命令 + 证据路径」；未跑命令不声称通过。

### 5.3 证据与版本纪律
- 证据文件：`计划书/e2e-evidence/<类型>-<版本/日期>.{json,png,md}`。
- 每批结束：`VERSION` bump + `workflow_status.md` 新节 + `project_specs.md` + `graft build`。
- 提交：约定式（feat/fix/docs/test/perf/ci）；推送 main；tag + Release（沙箱受限时在 Actions UI 触发 `release.yml`）。
