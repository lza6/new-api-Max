1. 上下文：为什么会做这一批

2026-10-23 09:03 / 09:05 UTC，生产 PostgreSQL 两次被 OOM killer 杀掉后端进程，触发崩溃恢复，统计信息被清空。09:05–09:06（本地 17:05–17:06）产生 147 个 503，用户反馈「服务器炸了、用不了」。

元凶是一条从 Postgres 日志里捞出来的 SQL：

SELECT (created_at + 28800) / 86400 AS day_key, COUNT(*) AS requests,
       COALESCE(SUM(request_bytes),0) + COALESCE(SUM(response_bytes),0) AS bytes
FROM "logs" WHERE type='2' AND created_at >= '<30天前>'
GROUP BY day_key ORDER BY day_key ASC

执行计划是 Parallel Seq Scan on logs，扫描 2642MB 堆表，实测 18.1 秒。容器只有 256MB 内存，page cache 被灌满后撞 cgroup 上限 → OOM。

2. 直觉与关键取舍

取舍一：先止血，还是先根治？

止血（加内存、关 JIT、改成本模型）能让今天的故障不再复现；根治（预聚合）才能让它明年也不复现。但根治要改数据链路，风险高。决定：先止血并验证，再在稳定的基础上做根治——因为如果在内存仍然吃紧的库上做 DDL 和回填，等于在漏水的船上换发动机。

取舍二：预聚合为什么只做 total 和 by-model？

维度值必须是字符串。数字维度（channel/user）要 CAST，而 PG 是 ::text、MySQL 是 CAST AS CHAR、SQLite 是 CAST AS TEXT——一旦引入方言分支，三库兼容就成了长期负担。所以只做字符串维度，牺牲六维报表的覆盖，换取「一套 SQL 三库通吃」。

取舍三：为什么「删窗口 + 重插」而不是 UPSERT？

GORM 的 OnConflict 在 MySQL 上曾渲染出空子句（ON DUPLICATE KEY UPDATE 后面什么都没有，直接 1064）。删+插在三库行为一致、容易推理，且窗口很小（2 天 × 2 维）。

6. 已知限制（诚实交代）

  • migrateLOGDB() 在生产不落 schema 变更：启动日志打印了 database migration started，但 log_daily_stats 没被创建，同批的 migrateLogTrafficIndex 也没生效。已把 AutoMigrate 兜底到使用点，根因仍未查清。
  • 三库只实测了 SQLite + PostgreSQL：MySQL 未跑（本机无实例）。日键已按项目既有约定改成整数取模，但未在 MySQL 上实跑。
  • 六维报表未预聚合：channel/user/group/token 仍是全窗口扫表，靠 60s Redis 缓存兜底。
  • SSH 仍允许密码登录：24h 内 16867 次撞库，已装 fail2ban，但改密钥需用户提供公钥（否则锁死）。
  • 内核 5.15.0-30 已 reboot-required 17 天，需维护窗口。
