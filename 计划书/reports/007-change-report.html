1. 上下文与直觉（Why）

本项目是正在生产运行的 AI API 网关（主站 freeapi.tingfengai.art / 副站 japi.tingfengai.art）。终局审计把项目当成「即将被真实用户/调用方/部署者拉起的产品」逐项核验，发现的问题都不是"代码片段缺失"，而是默认配置与真实行为不一致这类最危险的东西：

  • 直觉：限流中间件"挂上了" ≠ 生效——它读的配置默认关。这类"看起来有其实没用"的假功能，是审计第一优先级。
  • 直觉：审计日志"有表有函数" ≠ 记了失败——硬编码 Success:true 让失败尝试永久隐身，暴力破解无迹可寻。
  • 直觉：两处私网判定必须同集，否则按最宽的一处绕过。

3. 关键设计决策（It's subtle because…）

  • 日键不用 /86400：MySQL 的 / 是小数除法（返回 20729.5 而非 20729），跨库不一致。改用 x - (x % 86400)，SQLite/MySQL/PG 一致（已实测）。
  • 报表别名 dim_key：key 是 MySQL 保留字，AS key 直接语法错。
  • GORM AutoMigrate 不删索引：移除 tag 只对新建库生效，存量库必须显式 Migrator().DropIndex。
  • 失败审计归属：用户存在但密码错 → 归属真实 userId；不存在 → userId=0，仅按用户名/IP 关联；绝不记录密码。
  • 熔断器复用既有过滤点（ChannelHealthProbe → FilterChannelHealth），零额外路由改动，开关关时零行为变化。

6. 独立审查闭环（How we were wrong）

独立审查线程（6 维度）对本批报出 3 个阻塞级缺陷，全部成立，已修复 + 先红后绿：

阻塞项根因修复
C1 熔断探针被过滤谓词消费ChannelCircuitAllows 有副作用（置 probing），却在候选过滤期被多次调用 → 未选中候选静默烧令牌，渠道 Open 窗口内永不恢复拆成纯判定 ChannelCircuitAllows + 发请求前单飞的 AcquireCircuitProbe（接入 distributor）
C2 CGNAT 被当信任来源isWebProtectionTrustedSource 用 IsPrivateIP（补 CGNAT 后）→ CGNAT 外部来源豁免限流/封禁拆语义：新增 IsTrustedSourceIP（不含 CGNAT），Web 防护改用它
C3 失败审计未闭环 + 死代码禁用用户/DecodeJson 分支无审计；RecordLoginFailureLog 零调用删死代码 + 补禁用/加载失败/DTO 解析失败分支审计

这正说明"看起来完成"与"真闭环"的差距——审查线程的价值在于抓出我自己看不到的逻辑漏洞。
