1. 起点：三个"看起来很小"的用户上报

  1. 页面顶部多出一行字 X content="…" />
  2. 页面顶部一直显示一张「模型 / 计费方式 / 价格」表
  3. 主页要显示真实的访客数、日活月活、流量来源

前两个的根因都不是"模板没渲染"，而是服务端 SEO 注入的边界问题。

2. 直觉：这些 bug 有共同的形状

形状一：断言"存在" ≠ 断言"合法"

og:url 的替换串漏写了开头的 <meta property="og:url"， 整条标签被替换成非法文本。而 <head> 内的非空白文本会提前结束 head， 于是那行字被当成 body 内容渲染出来。 当时的测试只检查 og:locale 是否存在（它是拼接追加的，不受影响）—— CI 全绿，线上是坏的。

形状二：清理的边界没对齐

价目表是给爬虫看的，清理脚本只删 #spa-seo-content 容器 —— 而那张表被拼在容器之外，于是永远不会被删。 SPA 路由切换不重载文档，残留还会跟着走到别的页面。

这两条推出一个可复用判据：凡"替换/注入/清理"，必须断言结果的合法性与边界归属， 并加反向锁（如 NotContains("X content=")）。

4. 压测抓出的最有价值缺陷

对新增的公开统计端点做 12 并发 × 20 请求：

修复前：{"200":229,"TIMEOUT":11}  p50=206ms  p95=30146ms
修复后：{"200":240}              p50=214ms  p95=368ms

两个成因叠加：① 聚合本身 6.3 秒（DAU/MAU 是对大表 logs 做 COUNT(DISTINCT user_id)）； ② 缓存一过期，并发请求同时未命中、各跑一遍（缓存击穿）。

修法：进程内 SWR（有旧值立即返回 + 后台刷新）+ 单飞（done-channel 让并发共享在飞计算） + TTL 分层（小表 60s；昂贵的 DAU/MAU 30min）+ 启动预热。

注意：第一版只用 refreshing 标志，测试当场抓到冷启动 16 并发仍各算一遍。 这正是并发测试不可省的原因。

5. 我犯的错（写在这里，避免淡忘）

错一：改错了计费标签判据（v1.3.131 引入 → v1.3.132 回退）

我看到模型 quota_type=1 却显示成「按用量表达式计费」，去 price.ts 看到按 quota_type 分支，就据此改了服务端判据顺序。 错了：用户真正看到的标签由 billing-mode.ts 的 getBillingModeLabelKey 决定（先判 billing_mode）， 价格列走 model-price-cell.tsx 的动态阶梯分支；且这类模型实际扣费来自计费表达式。 我因此制造了一处新的前后端不一致。

错二：定义了清理函数却零调用

ForgetChannelHealth 写完没接线（注释还写着"由渠道删除路径调用"）， 正是本项目记录过的「库全绿、生产零调用」模式；而且删除路径有两条， 我最初只想到一条。

错三：把「秒级聚合」放在公开端点的请求路径上

且无单飞 —— 这就是 §4 那个超时的成因。

错四：写了会误报的告警

我判 CryptoSecret == SessionSecret 就告警，但生产是「未设 CRYPTO_SECRET、 已设 SESSION_SECRET」——此时密钥稳定，去重完全正常，却会每次启动报错。 误报会让真实告警被无视。

共同教训：判定"用户会看到什么"或"是否真的生效"时， 权威来源是承载该行为的那个组件/调用点，不是同一字段在别处的用法。

10. 测验（必须全部答对）

选完点"提交"查看对错与解释。全部答对才算通过。

Q1. 那行 X content="…" /> 为什么会被显示出来？

head 内的裸露文本会提前终止 head —— 这是"元数据"变成"可见文字"的关键。

Q2. 为什么这个 bug 当时 CI 是绿的？

"断言存在" ≠ "断言合法"。这是本批反复出现的 bug 形状。

Q3. 价目表为什么一直显示在页面顶部？

可见的附加内容必须在容器内；清理脚本已改为按 id 兜底移除。

Q4. 我在 v1.3.131 改错计费标签判据，根本原因是什么？

权威来源是渲染它的那个组件。已写进项目记忆。

Q5. 压测里访客端点出现 11 次 30 秒超时，两个成因是什么？

同期 /pricing 与 / 全部正常 → 是这条路径自身的设计问题。

Q6. 我的第一版 SWR 实现被测试抓出什么问题？

修法是用 done-channel 让并发等待在飞的计算。

Q7. 为什么那版 GEO 增强不能上线？

注入块对用户不可见，只能描述"页面真实是什么"。安全做法：只注入页面上确实存在且用户可见的内容。

Q8. 「一个 IP 一天只算一次」是怎么保证的？

"靠调用方记得"不是保证；schema 层的约束才是。

Q9. 「撤销全部会话」为什么要连 dashboard PAT 一起作废？

刻意放在一个函数里而不是改 8 个调用点 —— 调用点还会增加，逐个补必然漏一个。

Q10. 任务日志「操作类型」全显示 Unknown，根因是？

修法是 canonical 主键 + legacy 别名；并加跨语言契约测试（前端测试直接读后端 constant/task.go）。

Q11. 容器非 root 的改动，我是怎么在生产上线前验证的？

对照实验是关键：它证明那个 FATAL 与改动无关，而不是"看起来像"。

Q12. 状态页为什么不显示「99.9% 可用率」？

它只报可证明的事实：真实探测、真实日志计数（带窗口与开关状态）、真实心跳；用 null 表达"不可用"而不是 0。
