变更报告：首字延迟治理 · 实时可观测性 · 延迟拆解

版本 v1.3.68 → v1.3.71 · 全部已上线生产（freeapi.tingfengai.art）

1. 背景与直觉

用户反馈：「只要超过 300K 的请求，首字就被拉大，很难受」，且怀疑我们上传慢。

直觉上的头号嫌疑是5Mbps 上行带宽——网关把几十 MB 的 prompt 完整上传到美国上游，出口被打满。于是先做了两件事：出站请求体 gzip 压缩（省上传字节）+ 实时面板（看见真相）。

但实测推翻了直觉。 通过 httptrace 精确分段后发现： 
上游直连「到首个真实 token」：
  30KB  → 3.1s
 100KB  → 3.4s
 300KB  → 8.5s     ← 用户说的「300K 就慢」
 800KB  → 21.8s
而 2MB body 上传只要 0.36s

结论：延迟的 80%+ 在上游 prefill（算力处理 prompt），不是我们的上传。 压缩只能省上传，省不了上游。这正是「延迟拆解」这个功能的由来——让任何人一眼看出瓶颈在哪一段，而不是猜。

3. 核心机制：延迟拆解

用 net/http/httptrace.ClientTrace 在网关发起上游请求处采集四个时间点：

ConnectDone           → 建连（含 TLS）
WroteRequest          → 请求体写完上游（= 上传耗时）
GotFirstResponseByte  → 上游响应头到达（= 上游 prefill 起点）

面板每行「首字」带分段条，hover 看明细：

5. 自我审查发现的 4 个真实缺陷（已修）

1. 竞态：httptrace emit 锁外读取

emit() 在锁外读 connectDone/wroteDone/firstByte（锁内写、锁外读）。HTTP/2 下钩子跨 goroutine，构成 data race。改为同锁内快照再回调。

2. 尺寸：bodySize 对非可回放 body 返回 0

透传 + reasoning_effort 路径返回 *bytesReader，不满足 ReplayableBody → bodySize()=0 → 面板显示 0 B、压缩率算成 Infinity。改为压缩函数直接返回实测字节。

3. 精度：started_at 秒级截断

.Unix()（秒）导致 elapsed_ms 最多 999ms 误差。改 UnixMilli()。

4. 半实现：LivePhaseWaiting 永不驱动

并发排队在中间件层，早于注册表注册，该状态生产永不出现。删除，排队数量改由 concurrency.waiting 暴露；同时接线 streaming 阶段。

6. 另一个问题：400 input[3].call_id

归因：上游问题，非本网关。

客户端 chat 请求的 tool_calls[].id 为空 → 渠道 49 是 pass_through（原样转发）→ 上游（另一个 new-api 中转）内部做 chat→Responses 转换时，function_call item 缺 call_id → 上游 400。

证据：直连上游（不经网关）用空 id 复现完全相同的 400；正常 id 经网关 200；近 1h gpt-6-luna 100 成功 / 0 错误。

7. 测验（必须通过）

Q1. 生产大 prompt 首字延迟的主因是什么？
实测：上游直连 800KB prompt 首 token 21.8s，而 2MB 上传只要 0.36s。瓶颈在上游算力。
Q2. 出站压缩能改善首字延迟的哪一部分？
压缩减少发往上游的字节，省上传时间并缓解出口拥塞；但无法减少上游处理 prompt 的时间。
Q3. 压缩阈值从 1MB 降到 256KB 的原因？
1MB 阈值下 300K-1MB 的请求完全没压缩——正是用户反馈「超过 300K 就慢」的区间。
Q4. 延迟拆解用哪个机制采集？
httptrace 钩子采集 ConnectDone / WroteRequest / GotFirstResponseByte 三个时间点。
Q5. 400 input[3].call_id 是谁的问题？
直连上游（不经网关）用空 id 复现完全相同的 400；渠道 49 是 pass_through 原样转发。
Q6. 自我审查发现的 httptrace 竞态是什么？
锁内写、锁外读不保证可见性；改为同锁内快照三段耗时再解锁回调。
Q7. 面板「延迟拆解条」中蓝色段代表？
amber=上传，blue=上游首 token。蓝色段通常占大头，直接说明瓶颈。
